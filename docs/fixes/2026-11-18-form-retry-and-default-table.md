# แก้การบันทึกซ้ำเมื่อการเชื่อมต่อขาด และค่าเริ่มต้น View

วันที่: 18 พฤศจิกายน 2569

## ขอบเขตที่ผู้ใช้ยืนยัน

แก้เฉพาะสองเรื่องจากรายงานทดลองใช้งาน ได้แก่ การลองบันทึกซ้ำหลังการตอบกลับสูญหาย และ View หลักของตารางใหม่ที่ยังเริ่มเป็นรายการ ส่วนบัคการแปลงชนิดข้อมูลทั้งสามเรื่องยังไม่ได้แก้ในงานนี้

## เรื่องที่ 1 — การลองบันทึกซ้ำของฟอร์มเดิม

สถานะ: แก้ไขและทดสอบผ่าน

หลักฐานก่อนแก้: กรณีเซิร์ฟเวอร์บันทึกสำเร็จแล้ว แต่การตอบกลับไม่ถึงเบราว์เซอร์ เมื่อกดบันทึกอีกครั้งเกิดสองแถว ตามรายงาน `docs/reviews/2026-11-18-exploratory-testing.md` และภาพข้อมูลสมมติใน `artifacts/exploratory-2026-11-18/duplicate-after-network-retry.png`

สาเหตุ: เส้นทางเพิ่มแถวผ่านฟอร์มไม่มีรหัสสำหรับจำผลคำขอบันทึกครั้งเดิม การลองใหม่จึงกลายเป็นคำขอสร้างแถวใหม่ แม้หน้าจอจะมีคำเตือนเรื่องผลบันทึกไม่แน่นอนแล้ว

สิ่งที่เปลี่ยน:

- ฟอร์มที่เปิดใหม่มีบริบทและรหัสคำขอบันทึกเฉพาะ ใช้รหัสเดิมเมื่อส่งซ้ำหลังเน็ตขาด
- เซิร์ฟเวอร์ผูกคำขอกับผู้ใช้ แอป พื้นที่พัฒนา และรุ่นข้อมูลหลังการกู้คืน
- เก็บผลคำขอใน `_form_submissions` ภายในธุรกรรมเดียวกับแถว รายการลูก รูปภาพ และ Action หลังบันทึก
- คำขอเดิมและข้อมูลเดิมคืนผลเดิม ไม่สร้างแถว รูปภาพ หรือทำ Action หลังบันทึกซ้ำ
- ถ้าคำขอบันทึกสำเร็จแล้วแต่ผู้ใช้เปลี่ยนเนื้อหาในฟอร์ม จะปฏิเสธการใช้รหัสเดิมกับข้อมูลใหม่ด้วย HTTP 409 เพื่อให้ตรวจรายการล่าสุดก่อน
- หากครั้งก่อนตรวจข้อมูลไม่ผ่านและธุรกรรมยังไม่สำเร็จ สามารถแก้ข้อมูลแล้วส่งใหม่ได้ตามปกติ
- ฟอร์ม Reopen และการเปิดฟอร์มใหม่สร้างรหัสใหม่ จึงยังเพิ่มข้อมูลเนื้อหาเหมือนกันได้โดยตั้งใจ
- การเพิ่มผ่าน Ref ใช้กลไกเดียวกัน โดยไม่เพิ่มคำขอโหลดค่าเริ่มต้นให้ฟอร์มเพิ่มปกติที่มีบริบทอยู่แล้ว
- ถ้าเขียนผลคำขอไม่ได้ จะย้อนข้อมูลและล้างสำเนารูปที่สร้างในครั้งนั้นด้วย
- การแก้ไขแถวเดิมยังใช้กลไกตรวจเวอร์ชันแถวเดิม ไม่เปลี่ยนความหมายของ Action หรือ Workflow

การรักษาขนาดข้อมูลและการกู้คืน:

- ผลคำขอมีอายุ 24 ชั่วโมงนับจากบริบทฟอร์ม และล้างผลเก่าเมื่อมีคำขอบันทึกใหม่
- ฟอร์มเก่าที่หมดอายุจะถูกปฏิเสธ ให้ตรวจรายการล่าสุดแล้วเปิดใหม่ ไม่ส่งเป็นคำขอใหม่เงียบ ๆ
- การกู้คืนไม่คัดลอกผลคำขอจากข้อมูลเก่ามาใช้ในรุ่นข้อมูลใหม่
- รหัสคำขอของผู้ใช้ แอป หรือพื้นที่พัฒนาอื่นใช้ข้ามบริบทไม่ได้

ไฟล์หลัก:

- `lib/form-submission.ts`: ตรวจบริบท จำและคืนผลคำขอในธุรกรรม
- `lib/form-submission-schema.ts`: โครงสร้างตารางผลคำขอและดัชนีวันหมดอายุ
- `lib/form-submission-client.ts`, `lib/pending-images.ts`: รหัสคำขอของฟอร์มและการส่งพร้อมรูป
- `lib/form-images.ts`: ใช้เส้นทางบันทึกเดิมร่วมกับผลคำขอ โดยคงการย้อนกลับไฟล์
- `app/api/data/[table]/route.ts`: ส่งบริบทจากค่าเริ่มต้นและรับรหัสคำขอของฟอร์มเพิ่ม
- `app/components/RuntimeTable.tsx`: เริ่มรหัสใหม่เมื่อเปิดฟอร์มใหม่ และคงรหัสเมื่อทดลองบันทึกซ้ำ
- `lib/schema.ts`, `lib/db.ts`, `lib/backups.ts`: เตรียมตารางปฏิบัติการและรักษาความเข้ากันได้ของการกู้คืน

## เรื่องที่ 2 — ค่าเริ่มต้น View หลักของตารางใหม่

สถานะ: แก้ไขและทดสอบผ่าน

สาเหตุ: `createDefaultViews` กำหนดชนิด View หลักเป็น `list` โดยตรง

เปลี่ยนเป็น `table` เฉพาะ View หลักที่สร้างใหม่ หน้าแบบฟอร์ม/รายละเอียดและ Inline คงชนิดเดิม ไม่เปลี่ยน View รายการที่ผู้ใช้มีอยู่แล้ว

ปรับข้อมูลตั้งต้นของ Test ที่อ้าง View หลักด้วย `kind=list` ให้เลือกตามตำแหน่ง `primary` เพื่อให้ยังตรวจความพร้อมและการยกเลิกตารางร่วมเรื่องเดิมได้ โดยไม่ได้ลดข้อกำหนดหรือปิดความสามารถที่ทดสอบ

## ข้อจำกัดและความเสี่ยงที่เหลือ

- มีผลกับฟอร์มที่โหลดโค้ดรุ่นใหม่นี้ ผู้เรียก API เดิมที่ไม่ส่งรหัสคำขอยังคงใช้พฤติกรรมเดิมเพื่อรักษาความเข้ากันได้
- การปิดหรือรีโหลดแล้วเปิดฟอร์มใหม่ถือเป็นความตั้งใจเพิ่มรายการใหม่ ไม่ได้ห้ามข้อมูลเนื้อหาเหมือนกันทั้งระบบ และยังไม่มีระบบบันทึกฟอร์มออฟไลน์ข้ามการรีโหลด
- รูปอาจถูกส่งผ่านเครือข่ายอีกครั้งเมื่อลองบันทึกใหม่ แต่ไม่สร้างรายการรูปและไฟล์จัดเก็บซ้ำจากคำขอเดิม
- การส่งอีเมล/Push ของผู้ให้บริการภายนอกยังขึ้นกับกลไก Workflow และผู้ให้บริการเดิม ไม่รับรองการส่งภายนอกแบบครั้งเดียวทุกกรณี
- ยังไม่ได้ทดสอบบน iPhone หรือ VPS จริง
- ไม่มีการเปลี่ยนฐานข้อมูลจริงหรือ Deploy ในงานนี้
