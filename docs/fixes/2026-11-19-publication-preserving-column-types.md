# เผยแพร่การเปลี่ยนชนิดคอลัมน์โดยคงค่าข้อมูลเดิม

## ความต้องการ

เปลี่ยนคอลัมน์เดิมจาก Text เป็น Enum ในพื้นที่พัฒนา แล้วเผยแพร่กลับเวอร์ชันจริงได้ เมื่อข้อมูลจริงผ่านเงื่อนไขใหม่ โดยไม่บังคับแก้โครงสร้างในเวอร์ชันจริงก่อน

เดิมตัวตรวจและตัวดำเนินการอนุญาตเฉพาะเพิ่มตารางและคอลัมน์ จึงปิดการเปลี่ยนชนิดทั้งหมด แม้ไม่มีข้อมูลหรือชนิดใหม่ใช้รูปแบบจัดเก็บเดียวกัน

## ขอบเขตที่เพิ่ม

- Text, Longtext และ Enum เปลี่ยนสลับกันได้ โดยยังเก็บเป็นข้อความและไม่แก้ค่าข้อมูล
- Number และ Decimal เปลี่ยนสลับกันได้ โดยยังเก็บเป็น REAL
- ต้องเป็นคอลัมน์จริงของตารางภายในที่แอปเป็นเจ้าของ และไม่มีแอปอื่นเชื่อมตารางนั้น
- ชื่อ รหัสคอลัมน์ Key ความห้ามซ้ำ การเป็นคอลัมน์คำนวณ และตารางอ้างอิงต้องไม่เปลี่ยนพร้อมกัน
- เงื่อนไขใหม่ เช่น ตัวเลือก Enum, Valid_If และ Required ยังต้องผ่านการตรวจตามปกติ
- ตารางว่างก็ใช้เส้นทางซ้อมและเผยแพร่เดียวกัน

ยังไม่รองรับการลบ เปลี่ยนชื่อ Text เป็น Number, Ref, List หรือชนิดอื่นที่ต้องเปลี่ยนรูปแบบจัดเก็บหรือแปลงค่าข้อมูล รวมถึงตารางร่วม ขอบเขตนี้ตั้งใจแก้กรณี Text เป็น Enum ที่ผู้ใช้ยืนยันก่อน

## วิธีทำงาน

1. ตัวตรวจใช้กฎร่วมใน `lib/release-column-types.ts` เพื่อระบุคู่ชนิดที่คงรูปแบบจัดเก็บและค่าข้อมูล
2. ตัวซ้อมและตัวเผยแพร่ใช้กฎเดียวกัน ไม่ใช้เพียงผลตรวจจากหน้าเว็บ
3. ตัวดำเนินการตรวจชนิด SQL จริง และเปลี่ยนเฉพาะชนิดในข้อมูลตั้งค่าคอลัมน์ภายในธุรกรรมเดิม ไม่สร้างตารางทดแทน ไม่ UPDATE ข้อมูลธุรกิจ และไม่ลบ Trigger/Index
4. เปลี่ยนชนิดทุกครั้งต้องตรวจข้อมูลล่าสุดครบใน Worker ก่อนเผยแพร่ แม้เปลี่ยนเฉพาะชนิดโดยไม่เปลี่ยนเงื่อนไขอื่น
5. ใช้การตรวจรุ่นข้อมูลและสิทธิ์เดิมก่อน Commit หากมีข้อมูลใหม่ที่ไม่ผ่านเงื่อนไข จะไม่เผยแพร่
6. สำรองข้อมูลและใช้รหัสเผยแพร่ซ้ำตามกลไกเดิม หากเกิดปัญหาจะย้อนธุรกรรมทั้งหมด
7. เปลี่ยนรุ่นตัวดำเนินการเป็น v7 เพื่อให้ผลซ้อมจากโค้ดเดิมใช้ยืนยันไม่ได้ ต้องซ้อมใหม่หลังอัปเดตโค้ด

## การทดสอบ

- ก่อนแก้: Test การยอมรับ Text เป็น Enum ล้มเหลว ตาม `.test-data/publication-type-red.log`
- ชุดทดสอบทั้งหมดหลังแก้: ผ่าน 680 ข้อ ข้าม 7 ข้อที่ต้องใช้ Linux ไม่มีข้อที่ล้มเหลว ตาม `.test-data/publication-type-tests-final.log`
- ทดสอบตัวดำเนินการและนโยบาย: คงค่า รหัสแถว และ SQL ของตาราง/Trigger/Index เดิม ย้อนข้อมูลตั้งค่าหากขั้นตอนถัดไปล้มเหลว และตรวจพบค่าที่ไม่อยู่ในตัวเลือก Enum ตาม `.test-data/publication-type-targeted.log`
- ทดสอบ API ด้วยฐานข้อมูลแยก: สร้างพื้นที่พัฒนา แปลง Text เป็น Enum ซ้อม เผยแพร่ สำรองก่อนเผยแพร่ เรียกซ้ำไม่ทำงานซ้ำ และตรวจว่าค่าที่เพิ่มหลังซ้อมทำให้เผยแพร่ไม่ได้จนกว่าจะแก้ไข ตาม `.test-data/publication-type-api.log`
- ชุดเฉพาะแผน นโยบาย และตัวดำเนินการผ่าน 32 ข้อ ตาม `.test-data/publication-type-targeted-final.log`
- Production Build ผ่าน รวม TypeScript ตาม `.test-data/publication-type-build-final.log`
- ทดสอบบน Production Build ด้วยฐานข้อมูลแยกผ่านทั้ง 3 ชุด:
  - `.test-data/publication-type-publicationtypes-production.log`: เปลี่ยนชนิดทั้งตารางว่างและมีข้อมูล ตรวจข้อมูลที่เพิ่มหลังซ้อม สำรอง การเรียกซ้ำ และการเผยแพร่ในแอปที่ไม่ใช่แอปหลักโดยไม่กระทบแอปอื่น
  - `.test-data/publication-type-publicationformula-production.log`: เพิ่ม/แก้สูตร ตรวจข้อมูลล่าสุด ย้อนธุรกรรม และข้อมูลเกิน 2,000 แถว
  - `.test-data/publication-type-publication-production.log`: เพิ่มโครงสร้างเดิม สำรองข้อมูล ความพร้อมกัน สิทธิ์ ประวัติ และแยกแอป

## วิธีใช้งานหลังอัปเดตโค้ด

1. Build และเริ่มเซิร์ฟเวอร์ใหม่ตามขั้นตอนเดิม เพื่อให้ Worker และเว็บเป็นโค้ดรุ่นเดียวกัน
2. ใช้พื้นที่พัฒนาเดิมได้ หากข้อมูลตั้งค่าจริงยังไม่ขัดแย้งกับฐานตั้งต้น
3. ตรวจและซ้อมใหม่ ผลซ้อมเก่าจะหมดความใช้ได้ตามรุ่นตัวดำเนินการ
4. ถ้าข้อมูลจริงผ่านตัวเลือกหรือ Valid_If ของ Enum ให้ตรวจพร้อมเผยแพร่และยืนยันตามปกติ
5. หากมีค่าไม่ผ่าน ให้แก้ข้อมูลจริงหรือขยายเงื่อนไขในพื้นที่พัฒนาแล้วตรวจใหม่ ระบบจะไม่เปลี่ยนค่าข้อมูลจริงให้อัตโนมัติ

## ข้อจำกัด

ยังไม่ได้ Deploy หรือเปลี่ยนฐานข้อมูลจริง ผลทดสอบใช้ข้อมูลจำลองแยกเท่านั้น การรองรับชนิดอื่นที่ต้องแปลงข้อมูลต้องออกแบบแผนย้ายข้อมูลแยก ไม่อนุญาตเพียงเพราะตารางในพื้นที่พัฒนาว่าง
