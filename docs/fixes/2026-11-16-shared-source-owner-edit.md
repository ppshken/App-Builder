# แก้ข้อจำกัดการแก้คอลัมน์ของตารางที่แชร์

## อาการที่จำลองได้
แอปต้นทางเป็นเจ้าของตาราง แต่เมื่อมีแอปอื่นเชื่อมอ่านตารางนั้น API กลับปฏิเสธการแก้ไขคอลัมน์ด้วยสถานะ 409 และข้อความให้ยกเลิกการเชื่อม ทั้งที่แอปปลายทางมีระบบรีเจนอยู่แล้ว

หลักฐานก่อนแก้: .test-data/shared-owner-edit-red.log

## สิ่งที่เปลี่ยน
- แอปเจ้าของใช้ขั้นตอนแก้คอลัมน์เดิมได้ตามปกติ ไม่บล็อกเพียงเพราะมีแอปอื่นเชื่อม
- เพิ่มคอลัมน์ แก้ชื่อที่แสดง สูตร เงื่อนไข เปลี่ยนชื่อหรือลบคอลัมน์ และเข้าขั้นตอนตรวจแปลงชนิดข้อมูลได้ โดยยังตรวจข้อจำกัดของแต่ละขั้นตอนเดิม
- แอปปลายทางยังไม่มีสิทธิ์เปลี่ยนโครงสร้างต้นทาง แม้ได้รับสิทธิ์เพิ่มหรือแก้ข้อมูลแถว การตั้งชื่อแสดง Label และคอลัมน์คำนวณเฉพาะแอปยังใช้ส่วนตั้งค่าตารางร่วมเดิม
- รีเจนไม่ปฏิเสธการเปลี่ยนชื่อ ชนิด หรือลบคอลัมน์แบบเหมารวมอีกต่อไป แต่ตรวจค่าตั้งปลายทางกับโครงสร้างใหม่ในธุรกรรม หากมีข้อผิดพลาดจะไม่บันทึก snapshot ใหม่
- รักษา Label ของคอลัมน์ที่ยังอยู่ด้วยรหัสคอลัมน์จริง และรักษาคอลัมน์คำนวณเฉพาะแอป ล้างเฉพาะค่าทับที่อ้างคอลัมน์ที่ถูกลบไปแล้ว
- ตรวจชื่อชนกับคอลัมน์คำนวณเฉพาะแอปจากคอลัมน์ต้นทางทั้งหมด รวมกรณีเปลี่ยนชื่อ
- ยังป้องกันการเขียนแถวเมื่อโครงสร้างปลายทางยังไม่รีเจน และตรวจ token ซ้ำเมื่อโครงสร้างเปลี่ยนหลังเปิดผลตรวจ

## ข้อจำกัดที่ยังจำเป็น
การลบทั้งตารางขณะที่แอปอื่นเชื่อมอยู่ยังต้องยกเลิกการเชื่อมก่อน เพราะไม่มีตารางต้นทางให้รีเจนอีกแล้ว ข้อจำกัดนี้ใช้เฉพาะคำสั่งลบตาราง ไม่บล็อกการยกเลิกผลตรวจแปลงชนิดข้อมูล

หากเปลี่ยนชื่อหรือลบคอลัมน์ที่สูตรหรือหน้าจอปลายทางใช้อยู่ ต้องจัดการจุดอ้างอิงก่อนรีเจน ไม่ลบสูตรหรือค่าตั้งของแอปปลายทางเพื่อให้ตรวจผ่านโดยอัตโนมัติ การตรวจ Key Ref Unique ข้อมูลจริง และผลกระทบของการแปลงยังทำงานตามขั้นตอนเดิม

## ไฟล์หลัก
- lib/auth-api.ts: จำกัดการบล็อกตารางที่เชื่อมไว้เฉพาะการลบทั้งตาราง รักษาการตรวจเจ้าของและสิทธิ์เดิม
- lib/shared-tables.ts: รับโครงสร้างที่เปลี่ยนหลังตรวจผลกระทบ และเก็บค่าตั้งเฉพาะแอปตามรหัสคอลัมน์

## การทดสอบ
- แก้ชื่อที่แสดงและเงื่อนไขบังคับกรอกในแอปเจ้าของ
- แอปปลายทางเขียนไม่ได้ก่อนรีเจน และกลับมาเขียนได้หลังรีเจน
- เปลี่ยนชื่อและลบคอลัมน์ที่ไม่มีการใช้งาน พร้อมตรวจข้อมูลเดิม
- ตรวจ/ยกเลิกผลตรวจ/ยืนยันแปลงชนิดข้อมูล แล้วรีเจนปลายทาง
- ตรวจ Label และสูตรเฉพาะแอปไม่สูญหาย
- ปฏิเสธปลายทางแก้โครงสร้างจริง ปฏิเสธลบทั้งตารางที่ยังเชื่อม และปฏิเสธ token เก่า
- ทดสอบหน่วยยืนยันว่ากรณีสูตรปลายทางเสีย การรีเจนย้อนกลับ snapshot เดิม

หลักฐาน: .test-data/shared-owner-edit-browser.log, .test-data/shared-owner-edit-unit.log, .test-data/shared-owner-edit-unit-focused.log และ .test-data/shared-owner-edit-build.log

ทั้งหมดใช้ไฟล์และฐานข้อมูลทดสอบแยก ไม่เปลี่ยน Production หรือเผยแพร่ระบบให้ผู้ใช้จริง

## ผลตรวจรอบสุดท้าย
- ชุดทดสอบหลักผ่าน 626 ข้อ ล้มเหลว 0 ข้อ ข้าม 7 ข้อ รวม 633 ข้อ
- ชุดทดสอบตารางร่วมเฉพาะส่วนผ่าน 30 ข้อ รวมการรักษา Label หลังเปลี่ยนชื่อและการย้อน snapshot เมื่อสูตรผิด
- ทดสอบ API ต้นทาง/ปลายทางกับการแก้ เปลี่ยนชื่อ ลบคอลัมน์ แปลงชนิดข้อมูลและรีเจนผ่าน
- ทดสอบหน้าเว็บตารางร่วมเดิมผ่าน รวมการแชร์ นำเข้า Label/สูตรเฉพาะแอป สิทธิ์ การรีเจน และหน้าจอมือถือ: .test-data/shared-owner-edit-regression.log
- Build และการตรวจชนิดข้อมูลผ่าน ไม่มีการ Deploy หรือแก้ฐานข้อมูล Production
