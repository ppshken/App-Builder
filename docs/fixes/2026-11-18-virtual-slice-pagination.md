# ลดงานคำนวณก่อนแบ่งหน้าของ Slice ที่ใช้คอลัมน์คำนวณ

## ปัญหาที่แก้

View รถบัสที่ตรวจสภาพแล้ว ของ Inspection EDIT ใช้ Slice `ISNOTBLANK([last_inspection_id])` โดย Ref นี้เป็นคอลัมน์คำนวณ ระบบจึงกรองด้วย SQL ไม่ได้ และเคยคำนวณข้อมูลทุกคอลัมน์ของรถ 1,671 คันก่อนกรองเหลือ 267 คันแล้วแบ่งหน้า

งานนี้ปรับเครื่องอ่านข้อมูล ไม่เปลี่ยนสูตร Slice หรือความหมายว่ารถใดผ่านเงื่อนไข รถที่มีรายการเปิดค้างยังคงอยู่ตามสูตรเดิม ไม่แก้ฐานข้อมูลจริง ไม่เปลี่ยนโครงสร้าง และไม่ Deploy

## วิธีแก้

- เพิ่ม `lib/slice-memory-page.ts` ให้ตรวจสิทธิ์ระดับแถวด้วยข้อมูลจริงครบก่อน แล้วคำนวณเฉพาะคอลัมน์และสูตรที่จำเป็นต่อเงื่อนไข Slice ตัวกรอง และการเรียงลำดับ
- นับจำนวนรวมและเลือกหน้าจากผลที่ผ่านเงื่อนไข จากนั้นจึงเรียกเครื่องอ่านแถวเดิมเพื่อเตรียมข้อมูลเต็มของหน้าที่แสดง
- `lib/view-records.ts` รับค่าที่เตรียมไว้แล้วของหน้าปัจจุบัน รวมทั้งข้อผิดพลาด เพื่อใช้ต่อโดยไม่คำนวณซ้ำ เป็นการป้องกันค่าจากสูตรเช่น `UNIQUEID()` เปลี่ยนระหว่างกรองและแสดงข้อมูล
- เพิ่มทางอ่าน Ref ตามรหัสเดียวใน `ExpressionContext` โดยใช้ `project` และตัวตรวจสิทธิ์เดิม การดึงคะแนนของรายการเดียวจึงไม่คำนวณคะแนนของทุกแถวในตารางปลายทาง สูตรที่อ้างตารางทั้งชุดยังใช้ `getTable` เดิม
- `app/api/data/[table]/route.ts` ใช้แผนแบ่งหน้าใหม่นี้เฉพาะคำขอแบบแบ่งหน้าที่ใช้ทางกรองในหน่วยความจำ ไม่มีการจัดกลุ่ม แผนที่ การเจาะจงรหัส หรือข้อความค้นหาทั้งแถว
- การค้นหา Group By แผนที่ การอ่านรหัสเดียว และการอ่านทั้งหมด ใช้แผนเดิมต่อ ส่วนการอ่าน Ref ตามรหัสช่วยลดงานของเส้นทางเหล่านั้นได้โดยไม่เปลี่ยนสูตร

## หลักฐานการทดสอบก่อนแก้

- `.test-data/inspection-slice-red.log`: กรณีทดสอบแผนแบ่งหน้าใหม่ยังไม่ผ่านก่อนเพิ่มการทำงาน
- `.test-data/inspection-slice-ref-red.log`: การอ่าน Ref รหัสเดียวโหลด 4 แถวแทนที่จะเป็น 1 แถว

## ผลวัดกับข้อมูลจริงแบบอ่านอย่างเดียว

เปิดฐานข้อมูลด้วย `readonly: true` และ `fileMustExist: true` ใช้บริบทเจ้าของจำลอง อ่านเฉพาะบนเครื่องพัฒนา ไม่บันทึกค่าข้อมูลส่วนบุคคลลงรายงาน

| รายการ | ก่อนแก้ | หลังแก้ |
| --- | ---: | ---: |
| เวลาเตรียมข้อมูลกรองและหน้าแรก | 2,604 มิลลิวินาที | 529 มิลลิวินาที |
| รถที่ผ่านเงื่อนไข | 267 | 267 |
| จำนวนรถหน้าแรก | 25 | 25 |
| แถวปลายทางที่โหลดสะสม รวมการอ่านซ้ำ | 37,231 | 3,055 |
| ผลเปรียบเทียบข้อมูลหน้าแรกทุกคอลัมน์ | ตรงกัน | ตรงกัน |

หลักฐาน `.test-data/inspection-slice-comparison.log` ใช้เครื่องคำนวณก่อนแก้สำหรับค่าฐาน และอ่านข้อมูลด้วยขั้นตอนเดิมเทียบกับแผนใหม่ คำนวณแฮชของผลลัพธ์ที่จัดลำดับชื่อคีย์แล้ว รวมค่าคะแนน เกรด ชื่อ Ref ข้อผิดพลาด และสิทธิ์ของแถว ผลตรงกัน

นี่เป็นการวัดโมดูลอ่านข้อมูล ไม่ใช่เวลา HTTP บน VPS หรือเวลารวมทั้งหน้าจอ และเป็นการวัดหนึ่งรอบ ไม่ใช่ค่ารับประกันทุกคำขอ

## กรณีทดสอบที่เพิ่ม

- จำนวนรวม หน้าถัดไป หน้าที่เกินจำนวนจริง การเรียงลำดับ และตัวกรองเพิ่มเติม
- ข้อผิดพลาดของคอลัมน์ที่ไม่ใช้กรองต้องยังแสดงในแถวของหน้าปัจจุบัน
- ค่าของคอลัมน์ที่ใช้กรองต้องไม่ถูกคำนวณซ้ำจนเปลี่ยนไป
- สิทธิ์ระดับแถวทั้งตารางหลักและตาราง Ref ต้องยังมีผล
- Ref รหัสเดียวต้องอ่านเฉพาะรหัสนั้น แต่สูตรรวมทั้งตารางยังได้ข้อมูลครบ
- API ต้องส่งค่าคะแนน Ref ตรงกับการอ่านทั้งชุด และยังคืนรุ่นข้อมูลเพื่อใช้ตรวจการแก้ไขพร้อมกันได้
- ค้นหาแบบทั้งแถวต้องใช้ทางถอยเดิม และการเรียงคะแนนคอลัมน์คำนวณต้องได้ลำดับที่ถูกต้อง

ชุดทดสอบรวมหลังแก้ผ่าน 655 ข้อ ข้าม 7 ข้อ รวม 662 ข้อ หลักฐาน `.test-data/inspection-slice-unit.log` และชุดทดสอบเฉพาะก่อนรวม API ผ่าน 66 ข้อ หลักฐาน `.test-data/inspection-slice-targeted.log`

ผลตรวจรุ่นสุดท้าย:

- Build สำหรับ Production ผ่าน รหัสจบงาน 0 โดยใช้ฐานข้อมูล Build แยก หลักฐาน `.test-data/inspection-slice-build-final.log` รอบแรกเครื่องมือหยุดแจ้งเตือนความปลอดภัยของ Next.js รุ่นเดิม จึงรันซ้ำ ไม่มีการเปลี่ยนแพ็กเกจในงานนี้
- API และเบราว์เซอร์ของ Ref/Slice ผ่านทั้งหน้าถัดไป การเลือกคอลัมน์ การเรียงคะแนน ค้นหา ตัวกรอง จำนวนรวม สิทธิ์ระดับแถว และการใช้หน้าฟอร์มเดิม หลักฐาน `.test-data/inspection-slice-api-browser.log`
- Related เดิมผ่าน รวมฟอร์ม รายละเอียดมือถือ และสิทธิ์ระดับแถว หลักฐาน `.test-data/inspection-slice-related-browser.log`
- ชุด API เดิมผ่าน 18 ข้อ หลักฐาน `.test-data/inspection-slice-api.log`
- Slice/Action ผ่านทั้งการตั้งค่า ปุ่มแถว การยืนยัน/ยกเลิก การรีเฟรชหลังกรอง และการเพิ่มแก้ไขลบบนมือถือ หลักฐาน `.test-data/inspection-slice-automation.log`
- Workflow ผ่าน PDF รูปภาพ ลายเซ็น ตารางลูก การบันทึกไฟล์ Action เบื้องหลัง เหตุการณ์และตารางเวลา Webhook การทำซ้ำอย่างปลอดภัย และสิทธิ์ผู้ใช้ หลักฐาน `.test-data/inspection-slice-workflows.log`

## ข้อจำกัด

- เงื่อนไขคอลัมน์คำนวณยังต้องตรวจแถวผู้สมัครทั้งหมดเพื่อให้จำนวนรวมถูกต้อง เพียงไม่คำนวณทุกคอลัมน์ของแถวที่ไม่อยู่ในหน้า
- การค้นหาและการจัดกลุ่มที่ต้องใช้หลายคอลัมน์ยังไม่ใช้แผนแบ่งหน้ารุ่นนี้
- แคชเป็นของแต่ละคำขอ ไม่ใช้ข้อมูลร่วมกันระหว่างผู้ใช้ การเปลี่ยนสถานะจึงต้องอ่านตามสิทธิ์และข้อมูลของคำขอใหม่
- ฟีเจอร์นี้ไม่เปลี่ยนแพ็กเกจหรือเงื่อนไขด้านสถานะทางธุรกิจ
