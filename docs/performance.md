# การปรับประสิทธิภาพ

- รอหลังพิมพ์คำค้นประมาณ 200 มิลลิวินาที แล้วส่งคำขอเดียว ลดการอ่านข้อมูลระหว่างพิมพ์
- โหลดค่าเริ่มต้น สูตร และตัวเลือก Ref ของฟอร์มพร้อมกัน
- ตัวเลือก Ref ที่เรียงตาม id และไม่มีตัวกรอง/กฎสิทธิ์ระดับแถว อ่านและคำนวณเฉพาะ 500 แถวที่จะส่ง แทนอ่านทั้งตาราง กรณีมีเงื่อนไขยังตรวจครบก่อนจำกัดผล
- อ่านโครงสร้างตารางซ้ำครั้งเดียวภายในชุดการคำนวณสูตรของคำขอเดียว ไม่มีการแชร์ข้อมูลบัญชีระหว่างผู้ใช้
- ค้นหาตาราง Related เฉพาะตารางที่อ้างอิงจริง
- ใช้ตัวจัดรูปแบบวันที่ร่วมกัน แต่คำนวณ TODAY/NOW ใหม่ตามเวลาของแต่ละการประเมิน
- โหลดชื่อและรูปภาพ Ref ร่วมกันตามตารางปลายทาง ทั้ง API ข้อมูลและ View พิเศษ เมื่อหลายคอลัมน์อ้างตารางเดียวกัน จะรวม id แล้วอ่านเป็นชุดละไม่เกิน 500 รายการ
- คำนวณเฉพาะคอลัมน์ชื่อ/รูปภาพ Ref และคอลัมน์ที่สูตรเหล่านั้นอ้างถึง ไม่คำนวณสูตรหรือโหลด List อื่นในตารางปลายทาง โดยยังตรวจสิทธิ์แถวจากข้อมูลดิบครบทุกคอลัมน์ และไม่แชร์ผลระหว่างคำขอหรือผู้ใช้
- Inline View รวมอ่านชื่อ/รูปภาพ Ref ของหน้าปัจจุบันเป็นชุด และเตรียมคอลัมน์ที่ต้องคำนวณครั้งเดียวต่อหน้า
- ระหว่างแก้ฟอร์ม ตรวจการล้างตัวเลือก Ref เฉพาะช่องที่ Valid_If อ้างถึงช่องที่เปลี่ยน รวมการอ้างผ่านช่องคำนวณและ Ref ที่ถูกล้างต่อกัน หากแก้ช่องที่ไม่เกี่ยวข้องจะข้ามขั้นตอนนี้ การตรวจฟอร์มสำหรับแสดงผลและก่อนบันทึกยังทำครบตามเดิม

## ผลทดสอบบนเครื่องพัฒนา

ข้อมูลจำลอง 100,000 แถว: อ่านหน้า 25 แถวประมาณ 22 ms; ตัวเลือก Ref 500 แถวประมาณ 20 ms หลังเตรียม API แล้ว ตัวเลขรวมคำขอ localhost บน dev server ไม่รวมการเปิดหน้าและการ compile ครั้งแรก

สูตร CONCATENATE ที่ใช้ TODAY/NOW รวม 3 ครั้ง ประเมิน 5,000 รอบ ค่ากลางจาก 3 ชุด: ก่อนปรับ 1,084 ms หลังปรับ 35 ms เฉพาะการคำนวณสูตรนี้ ไม่ใช่ความเร็วรวมทั้งแอป

กรณี View มี Ref 2 ช่องอ้างตารางเดียวกัน รวม 600 id ที่ไม่ซ้ำ: การอ่านแถวปลายทางลดจาก 4 คำสั่งเหลือ 2 คำสั่ง อ่าน metadata ครั้งเดียว และไม่ประเมินสูตรข้ามตารางหรือโหลด List ที่ไม่เกี่ยวกับชื่อ/รูปภาพ ตรวจซ้ำด้วย `npm test` ในชุด `tests/reference-labels.test.cjs` ซึ่งครอบคลุมสูตรชื่อที่อ้างต่อหลายช่อง รูปภาพ สิทธิ์ระดับแถว ข้อมูลที่เปลี่ยนระหว่างคำขอ และสูตรชื่อที่ผิดพลาด

Inline View 10 แถว มี Ref 2 ช่องไปตารางเดียวกัน: การอ่านแถวปลายทางลดจาก 20 คำสั่งเหลือ 1 คำสั่ง และอ่าน metadata ของปลายทางครั้งเดียว ผลทดสอบฟอร์มยืนยันว่าการแก้ช่องที่ไม่เกี่ยวข้องไม่อ่านตารางสำหรับตรวจตัวเลือก Ref ส่วนการเปลี่ยนช่องต้นทางยังล้างตัวเลือกที่ใช้ไม่ได้ต่อกัน รวมถึงกรณีรายการลูกที่ยังไม่บันทึก จำนวนคำสั่งเหล่านี้ไม่ใช่ตัวเลขความเร็วรวมทั้งหน้า

ทดสอบข้อมูลจำลองแยกจาก data.db ด้วยคำสั่ง:

~~~powershell
npm test
node scripts/integration.cjs performance
node scripts/integration.cjs cache
node scripts/integration.cjs permissions
node scripts/integration.cjs pendingchildren
node scripts/integration.cjs partinline
~~~

สองชุดท้ายใช้ Microsoft Edge เป็นค่าเริ่มต้น หากติดตั้ง Google Chrome อยู่ ให้กำหนด `NOCODE_TEST_BROWSER=chrome` ก่อนรัน เช่น PowerShell ใช้ `$env:NOCODE_TEST_BROWSER = "chrome"` ส่วน macOS/Linux ใช้ `NOCODE_TEST_BROWSER=chrome node scripts/integration.cjs pendingchildren`

ความเร็วจริงขึ้นกับคอลัมน์ สูตร กฎสิทธิ์ ตัวกรอง และเครื่องที่ใช้งาน การค้นหาชื่อ Ref, เรียงช่องคำนวณ, Slice และกฎแถวบางรูปแบบยังต้องอ่านข้อมูลมากกว่าหน้าปัจจุบัน สูตรตัวเลือกข้ามตารางยังจำกัดที่ 10,000 แถวตามเดิม ผลแสนแถวข้างต้นเป็นตารางทั่วไปที่แบ่งหน้าด้วย SQL ไม่ครอบคลุมทุกกรณีดังกล่าว

ใช้งานประจำวันด้วย npm run build ตามด้วย npm start จะไม่เสียเวลา compile หน้าระหว่างใช้งานเหมือน npm run dev

## การปรับสำหรับมือถือ

- เก็บหน้าที่เคยเปิดพร้อมกันไม่เกิน 4 หน้าบนมือถือ/แท็บเล็ต และ 16 หน้าบนเดสก์ท็อป โดยเลือกเก็บหน้าที่เพิ่งใช้งานก่อน ลดจำนวนฟอร์ม รายการ และแผนที่ที่ค้างในหน่วยความจำ
- ระหว่างเลื่อน ใช้ตัวอ้างอิงพื้นที่เลื่อนที่เตรียมตอนเปลี่ยนหน้า แทนการค้นหา DOM ซ้ำทุก scroll event
- อุปกรณ์สัมผัสใช้เอฟเฟกต์จางสั้น ๆ แทนการเลื่อนทั้งหน้ารายละเอียดที่มีองค์ประกอบ fixed และยังเคารพการตั้งค่าลดภาพเคลื่อนไหว
- ทดสอบผ่าน Chromium จำลองหน้าจอมือถือและระบบสัมผัส รวมการเปิดข้อมูลหลายแถวและย้อนกลับ ผลนี้ไม่ใช่การวัดเฟรมเรตบน iPhone จริง

### โครงสร้างการเลื่อนบนมือถือ

หน้าระบบบนมือถือและแท็บเล็ตใช้กรอบแอพเต็มพื้นที่แสดงผล โดยเลื่อนเฉพาะ main ระหว่าง Header และ Navigation Bar แทนการเลื่อนเอกสารทั้งหน้า ป้องกันข้อมูลเลื่อนลอดออกนอกพื้นที่ Header/เมนูระหว่าง browser overscroll ตัวบันทึกตำแหน่งใช้ main.scrollTop บนมือถือ และ window.scrollY บนเดสก์ท็อป ทดสอบขอบบน–ล่าง การย้อนกลับ และบันทึกแก้ไขผ่านชุด backstate; ยังต้องยืนยันพฤติกรรม browser chrome บน iPhone จริง
