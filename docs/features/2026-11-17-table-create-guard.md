# เงื่อนไขเพิ่มข้อมูลและข้อความเมื่อเพิ่มไม่ได้

## ตั้งค่าที่ไหน

ไปที่ **Data → ตาราง → คอลัมน์ → ตั้งค่าตาราง**

เพิ่มช่อง:

1. **อนุญาตให้เพิ่มเมื่อ** — สูตรที่ต้องเป็นจริงก่อนเริ่มเพิ่มและก่อนบันทึก รองรับ SELECT และข้อมูลบัญชี พร้อมช่องสูตรและตัวช่วยเขียนสูตร
2. **ข้อความเมื่อเพิ่มไม่ได้** — ข้อความธรรมดาสูงสุด 500 ตัวอักษร หากเว้นว่าง ใช้ข้อความเริ่มต้น “ยังเพิ่มรายการใหม่ไม่ได้ กรุณาทำรายการก่อนหน้าให้เสร็จก่อน”

เว้นสูตรว่างเพื่อใช้พฤติกรรมเดิมตามสิทธิ์ ไม่มีการกำหนดสูตรให้ตารางจริงโดยอัตโนมัติ

## ตัวอย่างตรวจงานค้างของตัวเอง

```text
COUNT(
  SELECT(
    inspection[id],
    AND(
      [inspector] = USERID(),
      IN([status], LIST(1, 2))
    )
  )
) = 0
```

เปลี่ยน `inspection`, `inspector`, `status` เป็นชื่อในระบบจริง ตัวอย่างสมมติว่าผู้ตรวจเก็บ ID บัญชีผู้ใช้ และสถานะเป็นตัวเลขหรือ Ref ที่เก็บ ID 1, 2

สูตรนี้ไม่ใส่ในเงื่อนไขสิทธิ์ระดับแถว ข้อจำกัดเดิมของสิทธิ์ระดับแถวยังคงอยู่

## พฤติกรรมของปุ่มและฟอร์ม

- ผู้ใช้ที่ไม่มีสิทธิ์เพิ่ม จะยังไม่เห็นปุ่มเพิ่มตามระบบสิทธิ์เดิม
- ผู้ใช้ที่มีสิทธิ์เพิ่ม ยังคงเห็นปุ่ม + แม้เงื่อนไขธุรกิจไม่ผ่าน
- เมื่อกด + ระบบอ่านผลจากเซิร์ฟเวอร์ใหม่ ไม่ใช้ผลที่แคชไว้
- หากเป็นเท็จ ไม่เปิดฟอร์ม และแสดงข้อความสีแดงที่กำหนด พร้อมปุ่มรับทราบ
- หากเป็นจริง เปิดฟอร์มปกติ
- ก่อนบันทึก ตรวจซ้ำใน Transaction แบบจองการเขียนก่อนอ่านเงื่อนไข จึงไม่ให้สองคำขอผ่านพร้อมกันจากข้อมูลเดิม
- หากเปิดฟอร์มค้างไว้แล้วเงื่อนไขเปลี่ยน จะบันทึกไม่ได้และคงข้อมูลในฟอร์มให้แก้ต่อ
- การแก้ไขแถวเดิมไม่ใช้เงื่อนไขเพิ่ม เพื่อให้ผู้ใช้ทำงานค้างให้เสร็จได้
- การเพิ่มผ่าน Action, การนำเข้า และรายการลูกที่เรียกตัวบันทึกเดิม จะถูกตรวจด้วย ไม่ได้ตรวจเฉพาะปุ่มหน้าเว็บ

เพิ่มจุดตรวจก่อนเปิดรายการลูกจากรายละเอียด และก่อนอ่านค่าเริ่มต้นฟอร์มด้วย หากเปลี่ยนหน้าในระหว่างรอผลตรวจ ระบบยกเลิกคำขอตรวจที่ยังค้างอยู่

## ขอบเขตสูตรและสิทธิ์

เงื่อนไขถูกตรวจในขณะที่ยังไม่มีแถวใหม่ จึงใช้ข้อมูลบัญชีและการค้นด้วย SELECT ได้ แต่ไม่ใช้ `[คอลัมน์ของแถวใหม่]` โดยตรง หรือ Related ที่ต้องมีแถวแม่ปัจจุบัน

ไม่อนุญาต USERSETTINGS ในกติกานี้ เพราะผู้ใช้ปรับค่าเองได้

SELECT อ่านข้อมูลตามสิทธิ์บัญชีจริง รวมสิทธิ์ระดับแถว หากต้องนับงานค้างของผู้ใช้ ต้องให้ผู้ใช้นั้นมีสิทธิ์อ่านงานค้างของตัวเองด้วย ระบบไม่ได้ข้ามสิทธิ์การอ่านเพื่อไปนับแถวลับ

เงื่อนไขนี้เป็นกติกาของ **ตารางต้นทาง** ใช้กับทุกบทบาท รวมเจ้าของและแอปที่เชื่อมตารางเดียวกัน การตั้งค่ากติกาทำได้โดยผู้ที่แก้ไขตารางต้นทางได้ หากสูตรผิดระหว่างใช้งาน ระบบปฏิเสธเพิ่มและแจ้งให้ติดต่อผู้ดูแล ไม่ปล่อยให้เพิ่มผ่าน

## โครงสร้างและจุดเชื่อมต่อ

- เพิ่ม metadata `create_if`, `create_error` ใน `_tables` ค่าเริ่มต้นว่าง มีการย้ายโครงสร้างแบบเพิ่มช่องโดยไม่เปลี่ยนแถวข้อมูลธุรกิจ
- เพิ่ม `lib/table-create-guard.ts` สำหรับตรวจสูตรเบื้องต้นและประเมินกติกา โดยใช้เครื่องคำนวณสูตรเดิม
- เพิ่ม `GET /api/data/[table]?create_check=1` ผลปกติเป็น `{allowed, message}` ตรวจสิทธิ์อ่านและเพิ่มก่อนเสมอ
- ผลปฏิเสธบันทึกเป็น HTTP 422 พร้อมข้อความที่กำหนด การปฏิเสธสิทธิ์เดิมยังเป็น HTTP 403
- เพิ่มการตรวจใน `writeRecord()` ก่อนจัดสรรเลขรันและเพิ่มข้อมูล ภายใน Transaction เดิม ไม่สร้างเส้นทางบันทึกใหม่
- ยังคงการตรวจสิทธิ์ระดับแถว Validation Audit และ Automation เดิม
- ตัวเปิดฟอร์มแยกสถานะรอตรวจออกจากสถานะบันทึก เพื่อไม่ให้ไปชนตัวป้องกันเปลี่ยนหน้า
- การโคลนฐานข้อมูลใหม่แปลงชื่อตารางในสูตรให้ตรงกับตารางใหม่
- เพิ่มการตรวจสูตรในหน้าตรวจสุขภาพและระหว่างแปลงชนิดข้อมูล รวมการตรวจจุดอ้างอิงก่อนลบคอลัมน์และการเปลี่ยนชื่อคอลัมน์
- Metadata นี้อยู่ในรายการสำรอง/ฉบับร่าง/เผยแพร่ของตารางเดิม ไม่สร้างฐานข้อมูลอีกชุดเพื่อเก็บกติกา

## ข้อจำกัด

- เงื่อนไข SELECT ที่ซับซ้อนยังมีต้นทุนตามเครื่องคำนวณเดิม ควรใช้เงื่อนไขตรงและคอลัมน์ที่เหมาะกับการค้นหา
- การตรวจที่ปุ่มเป็นผล ณ เวลานั้น การตรวจตอนบันทึกเป็นจุดตัดสินสุดท้าย
- ไม่ได้ทดสอบบน iPhone จริง ใช้เบราว์เซอร์ทดสอบและข้อมูลจำลอง
- เครื่องมือแจ้งคำเตือนความปลอดภัย Next.js เดิมระหว่างตรวจ ไม่ได้อัปเกรด Dependency ในงานนี้
