# ระยะ 5 ส่วนแรก: เผยแพร่คอลัมน์คำนวณโดยตรวจข้อมูลล่าสุด

> อัปเดต: รองรับเงื่อนไขคอลัมน์ ตรวจข้อมูลล่าสุดใน worker แยก และยืนยันสิทธิ์อัตโนมัติแล้ว ข้อจำกัด 2,000 แถว/ต้องปิดสิทธิ์อัตโนมัติในเอกสารระยะก่อนถูกแทนด้วย [ขั้นตอนเผยแพร่รุ่นใช้งาน](2026-11-13-practical-schema-publication.md)

> ก่อน Deploy: การเผยแพร่โครงสร้างต้องเปิด `NOCODE_SCHEMA_PUBLICATION=1` หลังทดสอบ staging ค่าเริ่มต้นปิดไว้ ดู [คู่มือ Deploy รุ่นปัจจุบัน](../plans/2026-11-13-deploy-current-release.md)

วันที่: 13 พฤศจิกายน 2569

สถานะ: พัฒนาและทดสอบส่วนคอลัมน์คำนวณแล้ว **ยังไม่ใช่การเสร็จระยะ 5 ทั้งหมด** และยังไม่ได้ Deploy

## ขอบเขตที่เปิดเพิ่ม

- เพิ่มคอลัมน์คำนวณของตารางภายในที่แอปเป็นเจ้าของ โดยต้องมีสูตร และไม่มี Key/ห้ามซ้ำ/เงื่อนไขบังคับหรือเงื่อนไขรายการลูกที่กระทบการบันทึกเดิม
- แก้เฉพาะสูตรของคอลัมน์คำนวณเดิม โดยชนิดข้อมูลและการอ้างอิงยังคงเดิม
- ไม่สร้างคอลัมน์จริงสำหรับค่าคำนวณ ไม่คัดลอกค่าจากพื้นที่ทดลอง และไม่เขียนค่าคำนวณกลับลงแถวเดิม
- ตารางที่แอปอื่นเชื่อมอยู่ยังถูกบล็อก แม้แอปปัจจุบันเป็นเจ้าของ

ใช้หน้าเวอร์ชั่นแอปและปุ่มตรวจ/ซ้อม/เผยแพร่เดิม ต้องมีผลซ้อมเบื้องหลังที่ผ่าน ตรงกับแผน และยังไม่หมดอายุ จากนั้นตรวจพร้อมเผยแพร่และพิมพ์ข้อความยืนยันตามเดิม

## เหตุผลที่ต้องตรวจซ้ำก่อน commit

ผลซ้อมเป็นข้อมูล ณ เวลาหนึ่ง ระหว่างนั้นผู้ใช้ยังเพิ่มหรือแก้ข้อมูลจริงได้ ตัวอย่างสูตร `10 / [amount]` ซ้อมผ่านตอนค่ามากกว่าศูนย์ แต่ผู้ใช้อาจเพิ่มแถวที่ค่าเป็นศูนย์ภายหลัง

ทางเผยแพร่จึงเรียกตัวคำนวณและตัวตรวจแถวชุดเดียวกับงานซ้อมอีกครั้ง ภายในธุรกรรมที่ล็อกการเขียนแล้ว หลังใช้การตั้งค่าใหม่แต่ก่อนบันทึกเวอร์ชั่นสำเร็จ หากสูตรผิด ข้อมูลไม่ผ่าน เกินจำนวนแถว หรือเกินงบเวลา จะย้อนทั้งโครงสร้างและ metadata ไม่เกิดการเผยแพร่เพียงครึ่งเดียว

ไม่ใช้ลายนิ้วมือข้อมูลเก่าแทนการตรวจแถวจริง และยังคงการสำรอง การตรวจ session/สิทธิ์ซ้ำ การป้องกันคำขอซ้ำ และ receipt จากระยะ 4

## ขีดจำกัดที่ตั้งใจไว้

- เผยแพร่แผนคำนวณได้เมื่อจำนวนแถวรวมของตารางภายในที่แอปอ่านได้ไม่เกิน **2,000 แถว** ตรวจทั้งหน้ารีวิวและก่อน commit
- งบตรวจแถว **2 วินาที** ตรวจระหว่างและหลังคำนวณแต่ละแถว เป็นการตรวจเวลาแบบร่วมมือ ไม่ใช่การฆ่า process ที่กำลังคำนวณสูตรหนึ่งแถว จึงไม่รับรองว่าคำขอทั้งหมดเสร็จภายใน 2 วินาที
- ตรวจทุกตารางที่เกี่ยวข้องในขอบเขตแอป เพื่อให้ข้อผิดพลาดของสูตรที่พึ่งพาต่อกันทำให้แผนถูกปฏิเสธ ไม่เลือกตรวจเพียงแถวตัวอย่าง
- บริบทสูตรเป็นบัญชีผู้เผยแพร่ ไม่ได้พิสูจน์ผลทุกบทบาทหรือทุกค่าของสูตรที่เปลี่ยนตามเวลา เช่น `NOW()` จึงต้องทดสอบด้วยบทบาทจริงบน staging ด้วย
- ข้อผิดพลาดส่งเฉพาะจำนวนแถวที่ไม่ผ่าน ไม่มีค่ารายแถวหรือ stack trace
- แผนเพิ่มคอลัมน์จริงแบบเดิมที่ไม่มีการเปลี่ยนสูตรคำนวณยังไม่ถูกบังคับให้สแกนแถวทั้งหมด
- เพิ่มรหัสรุ่นตัวทำงานในลายนิ้วมือแผนแล้ว ผลซ้อมจากตัวทำงานระยะ 4 ใช้เผยแพร่รุ่นนี้ไม่ได้ ต้องซ้อมใหม่
- ข้อจำกัดฐานข้อมูล 512 MB และพฤติกรรมฟอร์มแก้ไขค้างที่อาจได้รับ 409 จากระยะ 4 ยังคงอยู่

กรณีที่ทดสอบจริง: เพิ่มคอลัมน์คำนวณ แก้สูตรเดิม ผลคำนวณจาก API ถูกต้อง แถวจริงเพิ่มหลังซ้อมจนสูตรผิดแล้วเผยแพร่ไม่ได้ metadata/เวอร์ชั่นย้อนครบ แก้สูตรแล้วซ้อมใหม่เผยแพร่ได้ ส่งคำขอซ้ำไม่เพิ่มเวอร์ชั่น ไม่มีคอลัมน์จริงหรือการเติมค่าคำนวณลงฐาน สูตรผิดในงานซ้อมถูกบล็อก เปลี่ยนเงื่อนไขคอลัมน์จริงยังถูกบล็อก และเกิน 2,000 แถวแสดงเหตุผลในหน้ารีวิว

ระหว่างสร้างชุดทดสอบแก้สมมติฐานของชุดทดสอบสองจุด: API เรียงแถวเริ่มต้นจากใหม่ไปเก่า จึงตรวจผลคำนวณโดยจับคู่รหัสแถว และ API เดิมไม่อนุญาตสูตรคำนวณบนคอลัมน์จริงอยู่แล้ว จึงใช้การแก้ Valid_If ทดสอบเส้นทางบล็อกเงื่อนไขแทน ไม่เปลี่ยนพฤติกรรมระบบเพื่อให้ทดสอบผ่าน

## งานระยะ 5 ที่ยังเหลือ

1. เปลี่ยนชื่อจากรหัสสายกำเนิด พร้อมตรวจการอ้างอิง สูตร View Slice Action Automation และฟอร์มรุ่นเก่า
2. แปลงชนิดและเติมข้อมูล: ใช้ตัวตรวจ/ตัวแปลงเดิม วัดเวลาจริง และกำหนดช่วงพักสำหรับข้อมูลใหญ่
3. ลบคอลัมน์/ตาราง: ต้องมีรายการผลกระทบและแผนเก็บข้อมูลที่ย้อนคืนรายแอปได้ ไม่คืนฐานทั้งระบบอัตโนมัติ
4. ตารางร่วม: ตรวจทุกแอปที่ใช้ข้อมูลเดียวกันและล็อกการเปลี่ยนที่ขัดกัน
5. ทดสอบ Linux/Docker staging การหยุด process ระหว่างงาน และฐานข้อมูลใกล้เพดานจริง

รายการเหล่านี้ยังถูกบล็อกในทางเผยแพร่ ไม่ได้เปิดใช้งานจากการเพิ่มคอลัมน์คำนวณรอบนี้ ไม่มีการเปลี่ยน Production Database หรือ Docker Volumes
