# ประสิทธิภาพสูตรและตัวช่วยเขียนสูตร

## ใช้งาน

เปิดตัวช่วยเขียนสูตร → แท็บ **ประสิทธิภาพ** ซึ่งอยู่ถัดจากคอลัมน์ ระบบประเมินโครงสร้างให้เมื่อแก้สูตร กด **ทดสอบและวัดประสิทธิภาพ** เพื่อใช้ค่าตัวอย่างเดียวกับแท็บลองคำนวณ โดยไม่บันทึกข้อมูลหรือรัน Action

ส่วนโครงสร้างแสดงภาระเบา / มีการอ่านหรือคำนวณเพิ่มเติม / ควรตรวจการคำนวณซ้อน พร้อมเหตุผลและแนวทางปรับ ดู SELECT ซ้อน, การอ่านทั้งตาราง, ORDERBY, Related, Ref, คอลัมน์คำนวณที่อ้างต่อ และ UNIQUEID ไม่ให้คะแนนเปอร์เซ็นต์หรือเดาเวลาจากข้อความสูตร

ส่วนผลวัดแสดงเวลารวมของรอบทดสอบ เวลาเตรียมข้อมูลสูตรบน server และเวลาคำนวณบนอุปกรณ์นี้ รวมถึงแถวที่โหลด แถวที่ SELECT ตรวจ และจำนวนครั้งใช้ผล SELECT เดิมซ้ำ มีรายละเอียดจำนวนโหลดชุดข้อมูล การใช้ข้อมูลที่โหลดไว้ การค้นผ่าน lookup, Related, ORDERBY และขั้นตอนตัวประเมิน

## ความหมายของผลวัด

- ประเมินจากโครงสร้างกับผลวัดจริงเป็นคนละส่วน ระดับโครงสร้างไม่ใช่การรับประกันว่าสูตรเร็วหรือช้า
- เวลารวมรวม HTTP/การรับและอ่าน JSON และการคำนวณฝั่ง client เวลาฝั่ง server วัดการเตรียม snapshot รวมการตรวจสิทธิ์และคำนวณค่าที่ต้องโหลด ไม่ใช่เวลา SQL เพียงอย่างเดียว
- แถวที่โหลดรวมเป็นแถวที่ผ่านสิทธิ์แล้ว นับการโหลด projection ซ้ำด้วย ไม่ใช่จำนวนแถวจริงทั้งหมดในตาราง จึงไม่เปิดเผยจำนวนแถวที่ผู้ใช้ไม่มีสิทธิ์
- SELECT rows นับแถวที่ตัวประเมินเข้าไปตรวจจริงหลังเลือก candidate ด้วย lookup และรวม SELECT ที่ซ้อนกัน ไม่ใช่จำนวนแถวในผลลัพธ์
- ขั้นตอนตัวประเมินเป็นจำนวนงานใน interpreter ไม่ใช่ CPU instruction หรือปริมาณงาน SQL ทั้งหมด
- ทดสอบกับค่าตัวอย่างหนึ่งชุด ไม่แทนผลทดสอบหลายแถว ผู้ใช้พร้อมกัน หรือ latency บน Production
- เปลี่ยนสูตรหรือค่าตัวอย่างแล้วผลเดิมถูกล้าง ยกเลิกคำขอเก่า และใช้ version guard ป้องกันคำตอบเก่าทับผลใหม่ ผลชนิดข้อมูลยังตรวจและปิดปุ่มใช้สูตรตามเดิม

## ปรับปรุงการคำนวณและโหลดข้อมูล

1. SELECT จากตารางซึ่งมีความหมายคงเดิมในหนึ่งรอบประเมิน เก็บผลไว้ใช้เมื่อถูกเรียกซ้ำในลูปเดียวกัน แยกผลตามโหมดค่า/รหัสแถว ไม่ใช้ cache ข้ามการประเมิน แถว ผู้ใช้ แอป หรือการเขียนข้อมูล
2. จำกัดการใช้ผลเดิมเฉพาะ SELECT จากตารางที่ไม่มี UNIQUEID, Related หรือ dereference ภายใน AST และ argument DISTINCT ต้องเป็น literal หากมี ตัวประเมินยังรักษา short-circuit และไม่เก็บผลข้อผิดพลาด งบการคำนวณเดิมไม่เพิ่ม
3. เปิด lookup และการใช้ SELECT เดิมซ้ำใน expressionContext ฝั่ง server, RuntimeTable ฝั่ง browser และการทดสอบในตัวช่วยสูตร Lookup ของ browser สร้างใหม่เมื่อ snapshot หรือข้อมูล draft เปลี่ยน
4. SQL projection ของสูตรอ่าน id/คอลัมน์ที่ต้องใช้ รวม Key/Label/Image/Ref และ dependency ที่จำเป็น แทน SELECT * สำหรับผู้ใช้ที่ไม่มีกฎสิทธิ์รายแถว ผู้ใช้ที่มีกฎรายแถวยังอ่านครบ เพราะกฎเดิม normalize ทุก physical field จึงคงพฤติกรรมความปลอดภัยเดิม
5. ตัวช่วยสูตรคำนวณเฉพาะคอลัมน์ที่สูตรต้องใช้และ dependency ไม่คำนวณ virtual column อื่นที่ไม่เกี่ยวข้อง ช่องตัวอย่างที่มีค่าแล้วไม่ขยาย default expression ที่ไม่ได้ใช้
6. POST expression-data โหลด dependency ของคอลัมน์ owner ที่ใช้งานเพื่อให้สูตรอ้างคอลัมน์คำนวณเตรียม snapshot ได้ครบ profile=true คืน {data, performance} ส่วนคำขอเดิมที่ไม่เปิด profile ยังคงรูปแบบเดิม สิทธิ์ POST ยังเป็น Builder ตามเดิม ไม่ผ่อนสิทธิ์เพื่อแสดงผลวัด
7. view-data ใช้ Slice SQL plan ที่รองรับเพื่อเลือกข้อมูลก่อนคำนวณแถวสำหรับกราฟ/ปฏิทิน/หน้าพิเศษ ยังคง permissions, interpreter ตรวจ Slice, ช่วงวันที่ และเพดานเดิมของหน้าพิเศษ สูตรที่ compile อย่างปลอดภัยไม่ได้ใช้ fallback เดิม

## ผลจริง

Benchmark สูตร SELECT ซ้อนด้วยตารางในหน่วยความจำ 280 แถว เปิด/ปิดการใช้ผล SELECT ซ้ำบนโค้ดเดียวกัน warm-up หนึ่งครั้ง วัดห้าครั้ง:

| งาน | แบบเดิม | เปิดการใช้ผล SELECT ซ้ำ |
| --- | ---: | ---: |
| แถวที่ SELECT ตรวจ | 78,680 | 560 |
| ขั้นตอน interpreter | 79,242 | 1,122 |
| มัธยฐานรอบนี้ | 12.09 ms | 1.80 ms |

ลดแถวที่ตรวจประมาณ 99.29% ในกรณีนี้ ตัวเลขเวลาขึ้นกับเครื่องและ workload ไม่ใช่ผลวัด Production ทำซ้ำด้วย `npm test` แล้ว `node tests/formula-nested-benchmark.cjs`

Regression กับ 12,000 แถวยืนยันสูตรซ้อนที่เคยเกินงบคำนวณสามารถคืนผล 10 ได้ ใช้ผลเดิมซ้ำ 11,999 ครั้งและตรวจ 12,010 แถว โดยไม่เพิ่มงบ การทดสอบตัวช่วยสูตรยังมี unrelated virtual expression 1/0 เพื่อยืนยันว่าไม่ได้คำนวณสิ่งที่ไม่ใช้
