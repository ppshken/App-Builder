# เวอร์ชั่นแอป ระยะ 3 รุ่นแรก — ซ้อมอัปเดตกับข้อมูลล่าสุด

วันที่: 12 พฤศจิกายน 2569

อัปเดต 13 พฤศจิกายน 2569: เพิ่มทางเผยแพร่โครงสร้างที่รองรับในระยะ 4 แล้ว ข้อจำกัดของรุ่นเดิมในเอกสารนี้ยังเป็นประวัติและขอบเขตทางเดิม ดู [การเผยแพร่โครงสร้างเพิ่ม](2026-11-13-additive-publication.md)

ปรับปรุงต่อแล้ว: ปุ่มซ้อมปกติใช้คิวเบื้องหลัง ข้อจำกัด 2,000 แถวในเอกสารนี้เป็นของรุ่นแรกและ API แบบเดิม ดู [งานซ้อมเบื้องหลังและข้อจำกัดล่าสุด](2026-11-12-rehearsal-background-jobs.md)

## สิ่งที่พัฒนาแล้ว

เพิ่มปุ่ม **ซ้อมอัปเดต** ในผลตรวจพื้นที่พัฒนาโครงสร้าง ระบบสร้างสำเนาฐานข้อมูลล่าสุดอีกชุดหนึ่ง แล้วทดลองเพิ่มโครงสร้างและใช้การตั้งค่าจากพื้นที่พัฒนาในสำเนานั้น ไม่ใช้ฐานข้อมูลทดลองทั้งก้อนแทนฐานข้อมูลจริง และไม่นำแถวทดลองเข้าผลซ้อม

ยังไม่เปิดเผยแพร่โครงสร้างกลับแอปจริง แม้ผลซ้อมผ่าน ปุ่มและ Backend ของการเผยแพร่ยังปฏิเสธพื้นที่พัฒนาเหมือนระยะ 2

## วิธีใช้งาน

1. เปิดเมนูเวอร์ชั่นแอป สร้างพื้นที่พัฒนาโครงสร้าง และทดลองเพิ่มตารางหรือคอลัมน์
2. กลับหน้าเวอร์ชั่นแอป กดตรวจและเผยแพร่ของพื้นที่นั้น
3. ในส่วนซ้อมอัปเดตกับข้อมูลล่าสุด กดซ้อมอัปเดต
4. อ่านผลผ่าน ไม่ผ่าน หรือยังไม่รองรับ พร้อมจำนวนข้อมูลก่อนและหลัง
5. หากข้อมูลหรือการตั้งค่าเปลี่ยน ผลเดิมจะแจ้งว่าเก่าแล้ว ให้ตรวจและซ้อมใหม่

## ขอบเขตที่ซ้อมได้

| งาน | พฤติกรรม |
|---|---|
| เพิ่มตารางภายในที่แอปเป็นเจ้าของ | สร้างโครงสร้างในสำเนาล่าสุด ตารางใหม่เริ่มที่ศูนย์แถว |
| เพิ่มคอลัมน์จริงในตารางเดิม | ต้องยอมรับค่าว่าง ไม่มี Key ห้ามซ้ำ ค่าเริ่มต้น เลขรัน หรือเงื่อนไขบังคับกรอก |
| เพิ่มคอลัมน์คำนวณ | ใช้ตัวตรวจสูตรและการคำนวณเดิม ตรวจค่ากับข้อมูลในสำเนา |
| การตั้งค่า View, Slice, Action และส่วนที่ระบบเผยแพร่เดิมรองรับ | ใช้ตัวนำการตั้งค่าเดิมและตัวตรวจความพร้อม ภายใต้บริบทสำเนา |
| ลบ เปลี่ยนชื่อ เปลี่ยนชนิด Key หรือโครงสร้างเดิม | รายงานว่ายังไม่รองรับ ไม่มีการฝืนรัน |
| โครงสร้างตารางร่วม รวมตารางของแอปเองที่แอปอื่นเชื่อมอยู่ | บล็อกจนกว่าจะรองรับการตรวจผลกระทบหลายแอป |
| ข้อมูลหรือการตั้งค่าแก้ไขชนกัน | บล็อก ไม่รวมการแก้ไขให้อัตโนมัติ |

ใช้ `columnDefinition`, `syncKeyIndex`, ตัวนำการตั้งค่าเดิมใน `lib/releases.ts`, `inspectApp`, `calculateRow`, `validateRow` และ `expressionContext` เดิม ไม่สร้างตัวประเมินสูตรใหม่ การแปลงชนิดยังไม่เปิดซ้อม จึงยังไม่มีการเรียกตัวแปลงชนิดในรุ่นนี้

## การตรวจและผลลัพธ์

- ตรวจลายนิ้วมือแผนที่ผู้ใช้เพิ่งรีวิว ก่อนเริ่มซ้อม และตรวจซ้ำหลังสร้างสำเนา
- บันทึกลายนิ้วมือข้อมูลล่าสุด ไม่บันทึกค่าแถวจริงลงรายงาน อ่านจำนวนเต็ม SQLite แบบ 64 บิตอย่างแม่นยำ เพื่อไม่ให้การปัดเศษของ JavaScript ทำให้ตรวจไม่พบค่าเปลี่ยน
- เปรียบเทียบค่าเดิมทุกคอลัมน์ของแถวเดิมก่อนและหลัง เพื่อป้องกันค่าข้อมูลเปลี่ยนโดยไม่ได้ตั้งใจ
- รายงานจำนวนแถวก่อนและหลัง รวมตารางใหม่ที่ต้องไม่มีแถวทดลอง
- ตรวจ Foreign Key และใช้ตัวตรวจสูตร/เงื่อนไขข้อมูลเดิมกับทุกแถวที่อยู่ในขอบเขตการซ้อม
- ผลมีอายุหนึ่งชั่วโมง การเปิดผลตรวจครั้งถัดไปตรวจแผนและลายนิ้วมือข้อมูลซ้ำ ไม่ใช้เพียงจำนวนแถวตัดสินว่าข้อมูลเดิม
- แสดงเฉพาะชื่อระบบตาราง จำนวน และรหัสตรวจ ไม่มีค่าข้อมูล รหัสผ่าน หรือข้อความข้อผิดพลาดที่อาจมีข้อมูลส่วนตัว
- Log ฝั่งเซิร์ฟเวอร์สำหรับความล้มเหลวมีรหัสงาน ขั้นตอน และชนิดข้อผิดพลาด ไม่พิมพ์ค่าข้อมูลหรือสูตรที่อาจมี Secret

ผลผ่านหมายถึงผ่านภายใต้ข้อมูล สิทธิ์ และเวลาที่ใช้ซ้อม ไม่ใช่การรับรองทุกบทบาทหรือทุกการกระทำของ Runtime และไม่ใช่สิทธิ์เผยแพร่

## การแยกพื้นที่และความปลอดภัย

- ใช้ `/api/releases` เดิม เพิ่มคำสั่ง `rehearse` รับเฉพาะรหัสพื้นที่และลายนิ้วมือแผน ไม่รับ SQL หรือชุดคำสั่งจาก Client
- ตรวจ Login, CSRF, สิทธิ์ผู้พัฒนา เจ้าของพื้นที่ แอป สถานะ และอายุพื้นที่ตามระบบเดิม
- ใช้โฟลเดอร์รหัสสุ่มแยกภายในพื้นที่พัฒนา โหมดโฟลเดอร์ `0700` และไฟล์ `0600` เมื่อระบบปฏิบัติการรองรับ
- ก่อนรัน DDL ต้องยืนยันไฟล์ฐานข้อมูลกับบริบทพื้นที่แยกและเครื่องหมายภายในสำเนา
- จับคู่รหัสคอลัมน์ใหม่กับรหัสในฐานซ้อม ไม่ใช้รหัสคอลัมน์จากฐานทดลองไปชนข้อมูลล่าสุด
- ขั้นตอนสร้างโครงสร้างและใช้การตั้งค่าอยู่ในธุรกรรมของสำเนา การทดสอบยืนยันการย้อนกลับเมื่อใช้การตั้งค่าล้มเหลว
- สืบทอดการปิด HTTP, Push, งานเบื้องหลัง และการเขียนไฟล์จริงจากระยะ 2
- ลบฐานซ้อมเมื่อคำขอจบทั้งกรณีสำเร็จและล้มเหลว ตรวจเส้นทางก่อนลบเฉพาะโฟลเดอร์รหัสงานที่คำขอนี้สร้าง
- เก็บเฉพาะรายงานล่าสุดแยกจากฐานข้อมูลทดลอง

การซ้อมไม่เปลี่ยนข้อมูลธุรกิจหรือโครงสร้างของแอปจริง แต่กลไก Session และประวัติคำขอปกติของระบบยังทำงานตามเดิม

## ข้อจำกัดที่ต้องทราบ

- รุ่นแรกจำกัดรวม 2,000 แถวของตารางภายในที่แอปอ่านได้ เกินแล้วรายงานล้มเหลว ไม่ใช้การสุ่มบางแถวแล้วบอกว่าผ่านทั้งหมด
- มีงบเวลา 15 วินาทีที่ตรวจระหว่างขั้นตอน/แถว ไม่ใช่การหยุดคำสั่ง SQLite กลางทาง การสร้างสำเนาและคำสั่ง SQL เดี่ยวอาจใช้เวลานานกว่านั้นได้
- การสร้างสำเนายังคัดลอกทั้ง SQLite และทำงานใน process แอป อาจใช้ดิสก์และกระทบความหน่วงบนฐานข้อมูลขนาดใหญ่ ต้องแยกงานและเพิ่มงบพื้นที่ก่อนรองรับงานใหญ่
- สำเนามีข้อมูลธุรกิจของฐานต้นทาง ไม่ใช่ข้อมูลที่ผ่านการทำให้ไม่ระบุตัวบุคคล แม้รายงานจะไม่แสดงค่าและเส้นทาง HTTP จำกัดตามแอป จึงต้องคุ้มครองพื้นที่จัดเก็บตามระยะ 2
- ไม่รองรับปุ่มยกเลิกงานกลางทางหรือการกู้สถานะงานหลัง process หยุด หาก process ถูกปิดก่อน `finally` อาจเหลือโฟลเดอร์ซ้อมส่วนตัว ต้องมีงานเก็บกวาดในระยะถัดไป
- ล็อกยังอยู่ใน process เดียว คำขอข้าม process อาจซ้อมแยกกันได้ แต่ใช้โฟลเดอร์คนละรหัสและไม่เปิดเผยแพร่จริง
- การแก้ metadata ของแอปอื่นบางส่วนยังทำให้แผนถูกบล็อกตามตัวเปรียบเทียบเดิม ไม่รวมการแก้ไขอัตโนมัติ
- ไม่ได้ทดสอบ Docker/VPS, iPhone เครื่องจริง, หนึ่งล้านแถว, การฆ่า process หรือการยกเลิกคำขอจากเครือข่ายในรอบนี้

## ลำดับต่อไป

ระยะ 4 ต้องเพิ่มตัวเผยแพร่จริงเฉพาะโครงสร้างเพิ่มอย่างเดียว พร้อมล็อกข้าม process สำรองก่อนแก้ ตรวจเงื่อนไขล่าสุด และบันทึกสถานะงานที่กู้ต่อได้ ผลซ้อมนี้ยังไม่ปลดล็อกการเผยแพร่ ไม่มีการ Deploy หรือเปลี่ยน Production Database ในงานพัฒนารอบนี้
