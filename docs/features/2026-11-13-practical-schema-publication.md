# เผยแพร่แผนพัฒนาที่มีเงื่อนไขคอลัมน์และข้อมูลมากกว่า 2,000 แถว

วันที่: 13 พฤศจิกายน 2569

## สิ่งที่รองรับเพิ่ม

- เพิ่มตารางและคอลัมน์จริงภายในของแอปตามเงื่อนไขที่รองรับ
- เพิ่ม/แก้สูตรคอลัมน์คำนวณ
- เปลี่ยน Required, Required_If, ค่าเริ่มต้น, Valid_If, Show_If, Editable_If, Reset On Edit และเงื่อนไขรายการลูกที่เป็นการตั้งค่า โดยตรวจความพร้อมและข้อมูลก่อนใช้
- แสดงผลของสิทธิ์อัตโนมัติสำหรับตารางและ Action ใหม่ ให้ยืนยันในหน้าเผยแพร่ ไม่ต้องปิดบทบาทเดิม
- ตรวจข้อมูลล่าสุดก่อนเผยแพร่ใน worker แยก ใช้ตัวซ้อมและตัวคำนวณเดิม ไม่ติดเพดานเผยแพร่ 2,000 แถว

ผู้ใช้ยังทำเพียง **ซ้อมผ่าน → ตรวจพร้อมเผยแพร่ → ยืนยันผลกระทบและสิทธิ์ → เผยแพร่** ไม่มีการบังคับแยกแผนที่เกี่ยวข้องกันเป็นหลายฉบับร่าง

## ขั้นตอนภายใน

1. ตรวจบัญชี สิทธิ์เจ้าของพื้นที่ แผน ผลซ้อม และการยืนยันสิทธิ์อัตโนมัติ
2. ถือสิทธิ์งานเผยแพร่ใน journal เดิม ป้องกันคำขอซ้ำและงานชนกัน
3. เก็บ revision ของข้อมูลที่เกี่ยวข้อง แล้วเรียกตัวซ้อมเดิมใน process แยกกับสำเนาข้อมูลล่าสุด โดยฐานต้นทางเปิดอ่านอย่างเดียว
4. ตรวจโครงสร้าง สูตร ข้อมูลอ้างอิง และเงื่อนไขบนสำเนา รองรับสูงสุดหนึ่งล้านแถว/15 นาทีตามตัวซ้อม ไม่เรียกการอ่านโค้ดว่าทดสอบข้อมูลแล้ว
5. ตรวจว่า revision ไม่เปลี่ยน สำรองฐานต้นทาง และตรวจบัญชี/สิทธิ์/แผนซ้ำ
6. เปิดธุรกรรมเขียน ตรวจ revision อีกครั้งแล้วจึงใช้โครงสร้างและ metadata พร้อม receipt ในธุรกรรมเดียว ไม่คำนวณสูตรทุกรายการระหว่างถือ writer lock
7. แจ้ง Runtime ด้วยกลไกเวอร์ชั่นเดิม โดยไม่บังคับรีโหลดฟอร์มค้าง

ถ้าข้อมูลเปลี่ยนระหว่างตรวจ ระบบยกเลิกก่อน commit และให้กดเผยแพร่อีกครั้งเพื่อตรวจล่าสุด ไม่ต้องสร้างพื้นที่พัฒนาใหม่เพราะการแก้ค่าแถวธรรมดา หากแผนหรือสิทธิ์เปลี่ยน ต้องตรวจและยืนยันผลกระทบใหม่

ผลตรวจล่าสุดที่ผ่านใช้ยืนยันภายใน commit ได้แม้ผลซ้อมก่อนหน้าเพิ่งหมดอายุระหว่างทำงาน โดยต้องเป็นผลของแอป พื้นที่ และแผนเดียวกัน รหัสผลตรวจล่าสุดถูกเก็บใน receipt เพิ่มจากรหัสผลซ้อมเดิม การส่งคำขอซ้ำใช้ receipt เดิม

## ตรวจข้อมูลเปลี่ยนโดยไม่ล็อกคำนวณทั้งฐาน

เพิ่ม `_release_data_versions` และ Trigger ที่ระบบจัดการ สำหรับตารางข้อมูลและข้อมูลผู้ใช้/บทบาท/การตั้งค่าผู้ใช้ที่เกี่ยวข้อง การเพิ่ม แก้ หรือลบข้อมูลจะเพิ่มตัวนับในธุรกรรมเดียวกับข้อมูล การ rollback จะย้อนตัวนับด้วย

ตัวนับทำงานทั้งตารางที่เปิดและไม่เปิด realtime จึงไม่พึ่งสถานะ realtime เพื่อรักษาความถูกต้อง ไม่ใช้ `last_seen` ของ session หรือ log การใช้งานเป็นเหตุให้ผลตรวจข้อมูลหมดอายุ

ก่อนเชื่อตัวนับ ต้องตรวจว่า Trigger ยังอยู่และตรงกับนิยามที่เชื่อถือได้ ถ้าถูกลบหรือแก้จากภายนอกจะปฏิเสธการเผยแพร่ ไม่มีการข้ามการตรวจโดยใช้เพียงชื่อตัว Trigger

ครั้งแรกที่เปิดโค้ดรุ่นนี้ มีการอัปเกรดโครงสร้างภายในเพื่อติดตั้งตัวติดตาม ไม่แก้ค่าของแถวงานผู้ใช้ อัปเดตตัวตรวจสำรอง/กู้คืนและแปลงชนิดให้รู้จัก Trigger ใหม่นี้อย่างเจาะจง ยังปฏิเสธ Trigger นอกระบบที่ไม่ตรงนิยาม และไม่เชื่อตัวนับที่นำเข้าจากไฟล์สำรอง

## สิทธิ์อัตโนมัติ

หน้าเผยแพร่แสดงบทบาทที่เปิดอัตโนมัติ ตารางใหม่พร้อมขอบเขตสิทธิ์ และ Action ใหม่ที่อยู่ในสิทธิ์ตาราง ต้องติ๊กยืนยันแยกก่อนเผยแพร่ API ตรวจ `automatic_grants_ack` ฝั่งเซิร์ฟเวอร์ด้วย ไม่อาศัยปุ่มใน UI อย่างเดียว

ใช้ `automaticRoleGrants` และกฎ `actionPermission` เดิม ผลสิทธิ์เกิดตามการตั้งค่าของบทบาท ไม่สร้าง role/grant definition ซ้ำ ไม่ปิดการตั้งค่าอัตโนมัติ และไม่ให้สิทธิ์ข้ามเพดานของตาราง/แอปหรือข้าม row rules เดิม

## การแจ้งข้อผิดพลาด

ถ้าตัวตรวจล่าสุดพบข้อมูลไม่ผ่าน API ส่งผลสรุปกลับและแสดงตาราง คอลัมน์ ประเภทปัญหา และจำนวนแถวใต้ปุ่มเผยแพร่ ไม่ส่งค่าจากเซลล์ รหัสแถว หรือ stack trace เมื่อ worker หยุด/หมดเวลา/คำขอถูกยกเลิก จะไม่มีการ commit โครงสร้างบางส่วน

สำเนาซ้อมล้างหลัง worker จบ ทั้งเส้นทางปกติและ parent ที่ตรวจพบ worker หยุด การดับทั้ง process แม่/เครื่องยังอาจทิ้งสำเนาส่วนตัวที่รอการเก็บพื้นที่พัฒนาตามอายุเดิม ไม่ใช่การล้างข้อมูลจริง

## วิธีเริ่มทดสอบ

1. บน localhost หยุดแล้วเปิด `npm run dev` ใหม่ เพื่อ Build worker และโหลดตัวติดตามรุ่นใหม่
2. ใช้พื้นที่พัฒนาเดิมได้ กดซ้อมใหม่หนึ่งครั้ง เพราะรหัสรุ่นตัวทำงานเปลี่ยน
3. กดตรวจพร้อมเผยแพร่ ตรวจรายการสิทธิ์ ติ๊กยืนยัน และพิมพ์ข้อความยืนยันตามหน้า
4. กดเผยแพร่ รอระบบตรวจข้อมูลล่าสุดและบันทึกผล ถ้าไม่ผ่านจะแสดงเหตุผลพร้อมตำแหน่ง ไม่ต้องเดาจากป้ายความเสี่ยง

สวิตช์ `NOCODE_SCHEMA_PUBLICATION=1` ยังต้องเปิดบนเซิร์ฟเวอร์ที่อนุญาตให้เผยแพร่ ไม่เปลี่ยน credentials หรือค่า Production ให้เอง

## ข้อจำกัดที่ยังต้องแยกงาน

- งานลบ เปลี่ยนชื่อ เปลี่ยนชนิด/Key/Unique และแก้โครงสร้างตารางร่วมยังไม่เปิดผ่านทางนี้
- Required/Valid_If ที่ทำให้ข้อมูลจริงไม่ผ่านยังถูกปฏิเสธพร้อมรายละเอียด ไม่แก้ข้อมูลหรือข้าม business rules ให้เอง
- ฐานข้อมูลเผยแพร่ยังอยู่ภายใต้ขีดจำกัดสำรอง/กู้คืนเดิม 512 MB
- ทดสอบจริงที่ 6,000 แถว ไม่ใช่หลักฐานว่าหนึ่งล้านแถวผ่านเวลาบน VPS ทุกขนาด
- สูตรขึ้นกับเวลาและบัญชี ตรวจตามเวลาของงานและบัญชีผู้เผยแพร่ ต้องทดสอบบทบาทใช้งานที่เกี่ยวข้องด้วย
- Docker/Linux/VPS runtime และการดับเครื่องกลาง commit ยังไม่ได้ทดสอบกับรุ่นนี้ ไม่ได้ Deploy

## ผลตรวจรอบปัจจุบันและการติดตั้ง

หน่วยทดสอบผ่าน 593 ข้อ ล้มเหลว 0 ข้อ ข้าม 7 ข้อสำหรับ POSIX Build ผ่าน ชุด API/เบราว์เซอร์ผ่านการเผยแพร่ 6,000 แถว การเผยแพร่เดิม สูตร งานซ้อม กู้คืนหลายแอป แปลงชนิด และ Realtime หลักฐานตามตารางข้างต้น ตัวตรวจ Compose/การบรรจุ worker ผ่านที่ `.test-data/practical-deployment-config.json` ซึ่งเป็นการตรวจ configuration ไม่ใช่การรัน Container Linux

กรณีข้อมูลใหญ่งานตรวจอาจเกิน 300 วินาที ต้องตั้ง timeout ของ reverse proxy สำหรับ `/api/releases` ให้รองรับเวลางาน (เช่น 1,200 วินาที) ก่อนใช้บน VPS ตัวอย่าง Nginx เดิมใช้ 300 วินาที การเปลี่ยนค่า proxy ต้องตรวจด้วย `nginx -t` บนเซิร์ฟเวอร์ ไม่ได้เปลี่ยน Nginx จริงให้เอง รอบนี้ทดสอบ localhost ผ่านฐานจำลอง ไม่มีการ Deploy

ภาพตรวจหน้าอนุมัติสิทธิ์และปุ่มเผยแพร่: `artifacts/practical-publication-confirmation.png` ทดสอบค่าเริ่มต้นกับการเพิ่มแถวจริงหลังเผยแพร่ และยืนยันว่า Valid_If ใหม่ปฏิเสธค่าที่ไม่ผ่านได้ด้วย ไม่ปรับ Expected Result เพื่อกลบข้อผิดพลาด ข้อคาดหวังนโยบายเดิมที่บล็อกฟีเจอร์ได้รับการปรับตามขอบเขตใหม่พร้อมทดสอบ backend จริง
