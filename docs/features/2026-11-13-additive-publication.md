# เวอร์ชั่นแอป ระยะ 4 รุ่นแรก — เผยแพร่โครงสร้างเพิ่ม

> อัปเดต: รองรับเงื่อนไขคอลัมน์ ตรวจข้อมูลล่าสุดใน worker แยก และยืนยันสิทธิ์อัตโนมัติแล้ว ข้อจำกัด 2,000 แถว/ต้องปิดสิทธิ์อัตโนมัติในเอกสารระยะก่อนถูกแทนด้วย [ขั้นตอนเผยแพร่รุ่นใช้งาน](2026-11-13-practical-schema-publication.md)

> ก่อน Deploy: การเผยแพร่โครงสร้างต้องเปิด `NOCODE_SCHEMA_PUBLICATION=1` หลังทดสอบ staging ค่าเริ่มต้นปิดไว้ ดู [คู่มือ Deploy รุ่นปัจจุบัน](../plans/2026-11-13-deploy-current-release.md)

วันที่: 13 พฤศจิกายน 2569

## ผลที่ได้

เพิ่มทางเผยแพร่จากพื้นที่พัฒนาไปยังแอปจริงสำหรับงานเพิ่มโครงสร้างที่รองรับ โดยรักษาตารางและแถวเดิม ไม่แทนฐานข้อมูลจริงด้วยฐานข้อมูลทดลอง และไม่นำแถวทดลองของตารางใหม่มารวม

พัฒนาและทดสอบกับฐานข้อมูลจำลองแล้ว ยังไม่ได้ Deploy หรือเรียกการเผยแพร่กับฐานข้อมูล Production

## วิธีใช้งาน

1. สร้างพื้นที่พัฒนาโครงสร้างจากเวอร์ชั่นแอป และแก้โครงสร้างในพื้นที่นั้น
2. กดตรวจและเผยแพร่ แล้วซ้อมอัปเดตเบื้องหลังให้ผ่าน
3. ในส่วนเผยแพร่โครงสร้างเพิ่ม กดตรวจพร้อมเผยแพร่
4. แก้เหตุผลที่บล็อกทั้งหมดก่อน ระบบต้องได้ผลซ้อมตรงแผนและยังไม่หมดอายุ
5. ติ๊กยืนยันผลกระทบและสิทธิ์ พิมพ์ `เผยแพร่โครงสร้าง` แล้วกดปุ่มเผยแพร่
6. ระบบสำรองข้อมูล ตรวจเงื่อนไขล่าสุด และ commit โครงสร้างกับการตั้งค่าในธุรกรรมเดียว
7. ผู้ใช้แอปเดิมได้รับข้อความว่ามีเวอร์ชั่นใหม่ โดยเลือกโหลดหลังบันทึกงานได้ ไม่มีการสั่งรีโหลดฟอร์มให้อัตโนมัติจากทางเผยแพร่ใหม่นี้

ระหว่างตรวจผลซ้อมซ้ำ ระบบไม่ล้างข้อความยืนยันที่กรอกไว้หากรหัสแผนยังเดิม แต่ถ้าแผนเปลี่ยนต้องยืนยันใหม่

## ขอบเขตที่เปิดในรุ่นแรก

| งาน | ผล |
|---|---|
| เพิ่มตารางภายในที่แอปเป็นเจ้าของ | เผยแพร่โครงสร้าง ตารางใหม่เริ่มที่ศูนย์แถว |
| เพิ่มคอลัมน์จริงในตารางเดิม | ต้องยอมรับค่าว่าง ไม่มี Key ห้ามซ้ำ เลขรัน ค่าเริ่มต้น หรือสูตร/เงื่อนไขใหม่ที่กระทบแถวเดิม |
| เพิ่มคอลัมน์ Ref ที่ว่างได้ | ใช้ความสัมพันธ์เดิมและสร้างดัชนี Ref โดยไม่ย้ายหรือเปลี่ยนรหัสแถวเดิม |
| ปรับชื่อแสดง ลำดับ Label และตัวเลือกรูปแบบที่อนุญาตของคอลัมน์เดิม | รองรับโดยไม่เปลี่ยนกฎข้อมูลเดิม |
| View, Slice, Action, Automation และการตั้งค่าอื่นที่ผ่านการตรวจเดิม | ใช้ตัวนำการตั้งค่าเดิมหลังโครงสร้างพร้อม |
| เพิ่มคอลัมน์คำนวณ หรือแก้สูตร/เงื่อนไขคอลัมน์เดิม | ยังบล็อก ต้องเพิ่มการตรวจข้อมูลและกลไกความสดแยกก่อน |
| ลบ เปลี่ยนชื่อ เปลี่ยนชนิด เปลี่ยน Key หรือเพิ่มเงื่อนไขรายการลูก | ยังบล็อก |
| แก้โครงสร้างตารางร่วม รวมตารางของแอปเองที่มีแอปอื่นเชื่อม | ยังบล็อก |
| เปลี่ยนการตั้งค่าตารางร่วมผ่าน overlay | ยังบล็อกในทางเผยแพร่รุ่นนี้ |
| เพิ่มตารางหรือ Action ขณะที่มีบทบาทเปิดสิทธิ์อัตโนมัติ | บล็อก ให้ผู้ดูแลจัดการก่อน ไม่มีการเพิ่มสิทธิ์ให้ทุกบทบาทเงียบ ๆ |

เจ้าของและผู้พัฒนายังใช้สิทธิ์ตามระบบเดิม ส่วนผู้ใช้ทั่วไปต้องได้สิทธิ์ตารางหรือ Action จากการตั้งค่าบทบาทจริง ทางเผยแพร่ไม่เพิ่มแถวสิทธิ์ให้เอง

## การตรวจข้อมูลล่าสุด

ผลซ้อมเป็นหลักฐานของสำเนาที่เคยตรวจ ไม่ถือว่าแถวจริงหยุดเปลี่ยนหลังซ้อม รหัสแผนซ้อมผูกกับ `RELEASE_EXECUTOR_VERSION` ด้วย เมื่อเปลี่ยนตัวทำโครงสร้างหรือนโยบายความปลอดภัยต้องเพิ่มรุ่นนี้ เพื่อไม่ใช้หลักฐานจากตัวทำงานรุ่นเก่า รุ่นแรกจึงจำกัดให้การเปลี่ยนโครงสร้างไม่ต้องเติมค่าหรือเปลี่ยนกฎของแถวเดิม

- ใช้ `CREATE TABLE` สำหรับตารางว่างใหม่ และ `ALTER TABLE ADD COLUMN` ที่ว่างได้สำหรับตารางเดิม
- ไม่มีคำสั่งนำแถวทดลองเข้า ไม่มี `UPDATE`, `DELETE`, แทนที่ หรือสร้างตารางธุรกิจเดิมใหม่เพื่อย้ายข้อมูล
- แถวที่ผู้ใช้เพิ่มหลังสร้างพื้นที่หรือหลังซ้อมจึงยังเป็นแถวเดิมในฐานข้อมูลจริง
- ตรวจแผน การตั้งค่า โครงสร้างจริง สิทธิ์ และผลซ้อมอีกครั้งภายในธุรกรรมเขียน
- ใช้ตัวตรวจความพร้อม สูตร การอ้างอิง และ Foreign Key เดิม ไม่เขียนตัวประเมินสูตรใหม่
- ไม่สร้างดัชนี Key/Unique ของตารางเดิมใหม่โดยไม่จำเป็น และรักษาดัชนี/Trigger ของตารางธุรกิจที่มีอยู่
- ปฏิเสธ Trigger นอกระบบบนตารางตั้งค่า เพราะอาจทำให้การบันทึก metadata มีผลข้างเคียงที่แผนไม่ได้กำหนด

การยอมให้ข้อมูลจริงเพิ่มหลังซ้อมเป็นพฤติกรรมที่ตั้งใจ ไม่ใช่การยอมให้แผนการตั้งค่าที่เปลี่ยนไปเผยแพร่ต่อได้ สูตรหรือเงื่อนไขที่อาจทำให้ต้องประเมินทุกแถวใหม่ยังไม่เปิดในรุ่นนี้

## สำรอง ธุรกรรม และหลักฐาน commit

สำรองด้วย SQLite backup แบบแบ่งหน้าไปยังโฟลเดอร์สำรองเดิม สร้างไฟล์ส่วนตัวด้วยโหมด `0600` ก่อนเขียนข้อมูล ชื่อไฟล์เข้ากับรายการสำรองเดิม และตรวจพื้นที่ว่างก่อนเริ่ม

รุ่นแรกจำกัดฐานต้นทางไม่เกิน **512 MB** ตามขีดจำกัดตรวจไฟล์กู้คืนเดิม และต้องมีพื้นที่ว่างอย่างน้อยสองเท่าของขนาดฐานบวก 64 MB การซ้อมเบื้องหลังยังมีเพดานของมันเอง จึงไม่ได้หมายความว่าทุกฐานที่ซ้อมได้จะเผยแพร่ได้ทันที

สำรองเป็นภาพข้อมูลก่อนเริ่มเปลี่ยนโครงสร้าง ผู้ใช้อาจเพิ่มแถวระหว่างสำรองกับ commit ได้ และแถวเหล่านั้นไม่ถูกทับ การคืนไฟล์สำรองทั้งฐานไม่ใช่วิธีย้อนเวอร์ชั่นแอปเดียวขณะผู้ใช้อื่นยังทำงานอยู่

ธุรกรรม `BEGIN IMMEDIATE` ครอบคลุม DDL, metadata, Audit Logs ที่เกี่ยวข้อง และแถวประวัติ `_app_versions` หากขั้นใดล้มเหลวให้ย้อนพร้อมกัน ไม่มีการเผยแพร่การตั้งค่าเพียงครึ่งเดียว

แถวเวอร์ชั่นเก็บ receipt ชนิด `additive-v1` พร้อมรหัสคำขอ แผน รุ่นตัวทำงาน ผลซ้อม ไฟล์สำรอง และเวลาใน `config_json._publication` ซึ่ง commit พร้อมโครงสร้างจริง เป็นหลักฐานหลักว่างานสำเร็จแล้ว

การส่งคำขอเดิมซ้ำคืนผลเดิมโดยไม่รัน DDL อีก แม้ process จะหยุดหลัง commit ก่อนส่งผลกลับ สถานะในไฟล์เสริมเสียหายหรือเขียนไม่ได้ก็ไม่เปลี่ยนข้อเท็จจริงจาก receipt ในฐานจริง

แยกสถานะพยายามเผยแพร่ใน `.app-releases/publications.db` ใช้ธุรกรรมและสิทธิ์ถือครองป้องกันงานข้าม process รันซ้อนกัน สิทธิ์มีอายุ 10 นาที หากหมดอายุก่อน commit ต้องตรวจใหม่ ไม่ปล่อย worker เก่าทำต่อโดยไม่ตรวจ

การเก็บพื้นที่พัฒนาใช้ตัวกันร่วมกับสถานะเผยแพร่ จึงไม่เก็บพื้นที่ขณะงานนั้นกำลังเผยแพร่ ส่วนการแก้โครงสร้างในพื้นที่ต้องผ่านลำดับล็อกเดิมและการตรวจ hash/ธุรกรรมของฐานพื้นที่

## สิทธิ์และการเปลี่ยนฐานระหว่างทำงาน

- API ใช้ Login, CSRF, สิทธิ์ผู้พัฒนา เจ้าของพื้นที่ และขอบเขตแอปเดิม
- ตรวจ Session และสิทธิ์อีกครั้งหลังสำรอง และภายหลังได้ล็อกเขียน ก่อนเปลี่ยนโครงสร้าง
- เปรียบเทียบ generation, connection และตัวตนไฟล์ เพื่อปฏิเสธเมื่อฐานต้นทางถูกกู้คืน สลับ connection หรือแทนไฟล์ในช่วงสำรอง
- ตรวจรหัสแผนรวมกับรุ่นตัวทำงาน โครงสร้าง SQLite และข้อมูลสิทธิ์ ไม่รับ SQL หรือค่าข้อมูลแถวจาก Client
- แสดงเฉพาะเหตุผลที่บล็อกและผลลัพธ์ที่จำเป็น ไม่ส่งค่าข้อมูลจริงหรือข้อความ constraint ที่อาจมีข้อมูลส่วนตัวกลับไป
- ไม่เปิดให้ย้อนโครงสร้างอัตโนมัติผ่านปุ่มย้อนเวอร์ชั่นเดิม เวอร์ชั่นชนิดนี้ต้องพัฒนาแผนรุ่นถัดไปแทน

## การแจ้งเวอร์ชั่นใหม่โดยรักษาฟอร์ม

เพิ่ม `release_revision` ใน SSE เดิมของแต่ละแอป เมื่อตัวเลขเวอร์ชั่นเปลี่ยนให้แสดงปุ่มโหลดเวอร์ชั่นใหม่กับภายหลัง โดยไม่บังคับนำทางหรือรีโหลดฟอร์ม

ทางเผยแพร่ใหม่นี้ไม่ส่งเหตุการณ์ `nocode:workspace` ที่เคยทำให้แท็บอื่นรีโหลดตาม และไม่สั่งรีโหลด metadata อัตโนมัติจากการเปลี่ยนสิทธิ์ที่มากับ snapshot การเผยแพร่เดียวกัน ทั้งนี้ Backend ยังตรวจสิทธิ์จริงทุกคำขอตามเดิม

ก่อนผู้ใช้เลือกโหลดใหม่มีข้อความให้บันทึกงานก่อน ปุ่มภายหลังปิดแจ้งเตือนโดยเก็บค่าฟอร์มไว้

## ไฟล์หลักและการใช้โครงสร้างเดิม

- `lib/release-publication-policy.ts`: เงื่อนไขเผยแพร่ที่แคบกว่าการซ้อมและตัวตรวจต้นทาง
- `lib/release-publication.ts`: ประสานสำรอง ตรวจสิทธิ์ ธุรกรรม receipt และการกู้สถานะ
- `lib/publication-journal.ts`: ล็อกสถานะข้าม connection/process และตัวกันเก็บพื้นที่
- `lib/release-rehearsal.ts`: แยกตัวทำโครงสร้างเพิ่มร่วมกัน ทางซ้อมยังต้องยืนยันฐานทดลอง ทางเผยแพร่ต้องอยู่ในธุรกรรมจริง
- `lib/releases.ts`: ใช้ตัวนำการตั้งค่าเดิม โดยทางใหม่ข้ามแถว metadata ที่ไม่เปลี่ยน และกันย้อนโครงสร้างผ่านทางเก่า
- `app/api/releases/route.ts`: เพิ่มการตรวจเผยแพร่และคำสั่ง `publish_development`
- `app/components/DevelopmentPublicationPanel.tsx`: ตรวจพร้อมเผยแพร่ ยืนยันผลกระทบ และยืนยันข้อความ
- `app/api/realtime/route.ts`, `app/components/RealtimeSync.tsx`: แจ้งเวอร์ชั่นใหม่โดยไม่ล้างงานค้าง

API เผยแพร่เดิมยังไม่รับพื้นที่พัฒนาโครงสร้าง ต้องใช้ทางใหม่ที่มีเงื่อนไขครบ ไม่ใช่ปลดตัวบล็อกเดิมแล้วส่งข้อมูลเข้าไปเฉย ๆ

ชุดเปรียบเทียบแผน Realtime ความพร้อมเผยแพร่ และซ้อมแบบเดิมรันก่อนการปรับตัวตรวจความพร้อมให้เห็น Ref ไปตารางใหม่ครั้งสุดท้าย ส่วนชุดเผยแพร่ พื้นที่พัฒนา และงานซ้อมเบื้องหลังรันซ้ำก่อนเพิ่มรหัสรุ่นตัวทำงานในแผนครั้งสุดท้าย จากนั้นรันชุดเผยแพร่และซ้อมเบื้องหลังซ้ำบน Build สุดท้าย

สิ่งที่ทดสอบจริง:

- เพิ่มตารางและคอลัมน์ รักษาแถวจริงล่าสุด รหัสเดิม และดัชนี/Trigger เดิมของตารางธุรกิจ
- ตารางใหม่ไม่มีแถวทดลอง ตรวจไฟล์สำรองแยกด้วย SQLite แบบอ่านอย่างเดียว
- กดเผยแพร่ผ่าน UI จริง ต้องยืนยันก่อน ปุ่มไม่ทำงานเมื่อยังไม่ครบเงื่อนไข
- ส่งคำขอพร้อมกันและส่งซ้ำได้หนึ่งเวอร์ชั่น ไม่มีการรัน DDL ซ้ำ
- บันทึก Audit Log ของคอลัมน์ที่สร้างจากการเผยแพร่จริง
- จำลอง constraint ของ metadata ล้มเหลวหลังสร้างตาราง แล้วตรวจว่าทั้งตาราง metadata และเวอร์ชั่นย้อนกลับ
- จำลองสถานะเสริมค้างหลัง commit และ Trigger ที่ขัดขวางการซ่อมสถานะ แล้วตรวจว่าผลจริงยังเป็น commit และไม่สร้างเวอร์ชั่นซ้ำ
- แยกการตั้งค่าของแอปอื่นและตรวจข้อมูลแอปแรกยังอยู่ครบ
- ปฏิเสธไม่มี Login, CSRF ไม่ถูกต้อง, ไม่ยืนยัน, ไม่มีสิทธิ์, ผลซ้อมหมดอายุ, แผนเก่า, บทบาทอัตโนมัติ, ตารางร่วม และ Trigger นอกระบบใน metadata
- เปิดฟอร์มค้าง กรอกข้อความ แล้วเผยแพร่จากอีกแท็บ ตรวจว่ามีแจ้งเวอร์ชั่นใหม่และค่าฟอร์มไม่ถูกล้าง ฟอร์มสร้างแถวเดิมยังบันทึกได้ ส่วนฟอร์มแก้ไขแถวเดิมได้รับ 409 จากการตรวจเวอร์ชั่นโดยเก็บค่าที่กรอกไว้
- ตัวกันการเปลี่ยน connection/generation/ไฟล์ และตัวกันเก็บพื้นที่ตรวจด้วยหน่วยทดสอบ ไม่ถือว่าเป็นการกู้ฐานจริงกลางงาน

## ข้อจำกัดและความเสี่ยงคงเหลือ

- ตรวจพบ Docker CLI แต่ Docker daemon ของบริบท Linux ในเครื่องไม่พร้อมใช้งาน (หลักฐาน `.test-data/publication-docker-check.log`) จึงยังไม่ได้ทดสอบ Docker/Linux/VPS จริง ไฟดับ ฆ่า process กลาง DDL หรือกู้ฐานจริงระหว่างเผยแพร่ กรณีสถานะค้างเป็นการจำลอง และกรณีย้อน DDL เป็น constraint failure จริงในฐานทดสอบ
- ทดสอบล็อกสถานะข้าม SQLite connection และ HTTP พร้อมกัน แต่ยังไม่ได้รันสอง Container เผยแพร่จริงพร้อมกัน
- การสำรองแบ่งหน้าไม่รันงานทั้งหมดแบบ synchronous แต่ช่วง DDL/ตรวจอ้างอิงเป็นงานใน process เว็บ และ SQLite จะล็อกเขียนชั่วคราว ไม่รับรอง zero downtime หรือเวลารอสูงสุดบนข้อมูลจริงขนาดใหญ่
- ไม่ได้วัดเวลารอบเผยแพร่บนฐานใกล้ 512 MB หรือหนึ่งล้านแถว
- ฟอร์มสร้างแถวที่เปิดก่อนเผยแพร่ทดสอบว่าบันทึกได้ แต่ฟอร์มแก้ไขแถวเดิมอาจได้รับ 409 เพราะรหัสตรวจแถวเดิมรวมโครงสร้างคอลัมน์ด้วย ระบบเก็บค่าที่กรอกและไม่บันทึกทับ ต้องตรวจข้อมูลล่าสุดก่อนส่งใหม่ ยังไม่ได้เปลี่ยนกลไก optimistic concurrency เดิม
- การสลับพื้นที่ด้วย Cookie และการกู้คืนทั้งระบบยังใช้กลไกเดิม ต้องแยกจากการเผยแพร่แอป ระยะนี้ไม่ได้เปลี่ยนให้เป็นพื้นที่ต่อแท็บอย่างสมบูรณ์
- ไฟล์สำรองเป็นทั้ง SQLite และอาจมีข้อมูลทุกแอป ต้องคุ้มครองพื้นที่จัดเก็บ และไม่คืนทั้งไฟล์เพื่อย้อนแอปเดียวโดยอัตโนมัติ
- การเผยแพร่ที่ล้มเหลวหลังสำรองเสร็จอาจเก็บสำรองไว้เพื่อการตรวจสอบ ไม่ลบประวัติที่สมบูรณ์ให้อัตโนมัติ

ขั้นถัดไปคือทดสอบบน staging ที่เหมือน Linux/Docker จริงและวัดช่วงล็อก ก่อนขยายไปยังคอลัมน์คำนวณ สูตร การแปลงชนิด เปลี่ยนชื่อ ลบ และตารางร่วมในระยะ 5
