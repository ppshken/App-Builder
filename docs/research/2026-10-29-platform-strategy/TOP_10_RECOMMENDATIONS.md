# TOP 10 ฟีเจอร์ที่เหมาะกับ Repository นี้

จัดทำวันที่ **29 ตุลาคม 2026** โดยวิเคราะห์โค้ดจริงและเอกสารทางการของ 10 แพลตฟอร์ม รอบนี้สร้างเฉพาะเอกสาร ไม่แก้ Source Code ฐานข้อมูล หรือระบบที่กำลังใช้งาน

ข้อเสนอหลักคือ **ทำให้แกนของระบบใช้ซ้ำ ขยาย และตรวจสอบการเปลี่ยนแปลงได้ ก่อนเพิ่ม AI หรือเปิดระบบปลั๊กอินเต็มรูปแบบ** คงสถาปัตยกรรมแบบ modular monolith และ SQLite เป็นฐาน แล้วแก้คอขวดตามผลวัด ไม่เริ่มจากการเขียนระบบใหม่

## ผลสำรวจที่ใช้ตัดสินใจ

สำรวจรายการไฟล์และจุดเชื่อมโยง 554 ไฟล์ พบ 50 API routes, 25 pages และจัดทำความสามารถ 47 รายการพร้อม File:Line: พบ implementation 33 รายการ, รองรับบางส่วน 7 รายการ, ยังไม่พบ 6 รายการ และข้อมูลไม่พอตัดสิน 1 รายการ ตัวเลขนี้เป็นผลวิเคราะห์โค้ด ไม่ใช่จำนวนฟีเจอร์ที่ทดสอบ Runtime ผ่าน

ระบบมีหลายแอปและตารางร่วม, สิทธิ์รายแอป/ระดับแถว, View 9 รูปแบบ, ตัวออกแบบหน้าจอ, สูตร, ฟอร์มและ Related inline, Actions, Automation, PDF, Excel, Realtime, PWA, แคช IndexedDB, ฉบับร่าง/ย้อนการตั้งค่า, สำรองข้อมูล และรายงานการทำงานแล้ว จึงควรต่อยอดของเดิมเหล่านี้

ศึกษาตลาดจากแหล่งทางการ 45 รายการ พร้อมวันที่ตรวจ สถานะ และข้อจำกัดของแผนบริการ มี Backlog 36 ข้อ และตัวเลือกไลบรารี 10 ตัวที่ตรวจ License แล้ว การศึกษาครั้งนี้ไม่ได้ทดลองบัญชีคู่แข่งหรือวัดประสิทธิภาพระบบจริง

## Top 10

ลำดับนี้พิจารณาผลลัพธ์ที่ผู้สร้างแอปได้รับร่วมกับโครงสร้างของ Repository ส่วนงานพื้นฐาน E03, G02, L01, A03 และ J03 ยังต้องอยู่ในแผน แม้ไม่ใช่ชื่อฟีเจอร์ที่ผู้ใช้เห็นโดยตรง คะแนนแบบถ่วงน้ำหนักครบทั้ง 36 ข้ออยู่ใน Roadmap

## สิ่งที่ต้องทำก่อนเพื่อรองรับ Top 10

- **A03 Dependency graph:** ใช้แผนผัง Ref และตัวตรวจสูตรเดิม เพิ่มการเห็นผลกระทบต่อ View, Action, PDF, Workflow, สิทธิ์ และแอปอื่น
- **E03 Delivery ledger/recovery:** Workflow มี transactional enqueue, checkpoint, Idempotency-Key และ manual retry แล้ว ให้เพิ่มหลักฐานการส่งแต่ละครั้ง สถานะผลลัพธ์ที่ยังไม่แน่นอน และนโยบายกู้คืน ไม่สร้างคิวใหม่ซ้ำ
- **G02 Secret broker:** ต่อจาก env token ที่มีอยู่ เพื่อแยก credentials ต่อแอป/การเชื่อมต่อ หมุนเปลี่ยนได้ และไม่ติดไปกับแพ็กเกจหรือ AI context
- **L01 Registry:** นำ built-in components/actions มาอยู่ใต้สัญญากลางก่อนรองรับคอมโพเนนต์ใช้ซ้ำหรือปลั๊กอิน
- **J03 Observability:** ต่อจาก metrics/logs เดิม ให้เชื่อม trace เก็บสถิติที่จำเป็น และแจ้งเตือนตามเกณฑ์

| หลายแอปและ shared datasets | ขอบเขตองค์กร/tenant, quotas และการแยกข้อมูลครบทุกช่องทาง |

## Roadmap ที่นำไปเริ่มงานได้

| ระยะ | ผลลัพธ์หลัก |
|---|---|
| **0–30 วัน** | F01 จำลองสิทธิ์, A03 ตรวจผลกระทบ, K03 สร้างเอกสารแอปจาก metadata และ A01 เฉพาะ specification spike |
| **31–90 วัน** | A01 แพ็กเกจการตั้งค่า, E03 delivery recovery, G02 secret broker; เริ่ม spike ของ Registry/แม่แบบ |
| **3–6 เดือน** | Query Planner, Registry และคอมโพเนนต์ใช้ซ้ำ, REST แบบอ่านอย่างเดียว และแม่แบบแอป |
| **6–12 เดือน** | งานอนุมัติ, Test Studio, ส่งรุ่นแอปข้าม environment, AI สูตรแบบ closed pilot และ UX/observability ตามงบกำลังทีม |

สมมติทีม 2 full-stack + 0.5 QA + 0.2 UX/Product จัดสรร 65% ให้ฟีเจอร์ใหม่ จะมีกำลังประมาณ 35 person-days/เดือน หรือ 420 ต่อปี แผนนี้เลือกบางส่วนจาก Backlog ทั้งหมดที่ประเมิน 659–1,062 person-days จึงไม่ได้สัญญาว่าทำครบ 36 ข้อในปีแรก ถ้าทำคนเดียวต้องลด scope หรือขยายเวลา

## สิ่งที่ไม่ควรทำตอนนี้

- เปิดร้านปลั๊กอินสาธารณะหรือรัน JavaScript/SQL/npm ที่ไม่ผ่านการตรวจใน server process
- ให้ AI แก้ Live, Publish, ลบข้อมูล หรือเพิ่มสิทธิ์เอง
- เปลี่ยนจาก SQLite หรือแตก microservices เพียงเพราะจำนวนแถวเพิ่ม โดยยังไม่วัด query, contention และ workload
- ย้าย Runtime เป็น Flutter/native เพื่อเลียนแบบคู่แข่ง ทั้งที่ Web/PWA ยังตรงเป้าหมาย
- Copy engine ของคู่แข่งเข้าแพลตฟอร์มโดยไม่ตรวจ License ของรุ่นและรูปแบบใช้งานจริง
- เปิด AUD-002/AUD-003 ที่ผู้ใช้สั่งพักกลับมาเอง งานวิจัยไม่ใช่การอนุมัติแก้นโยบาย Login, อัปเกรด Framework หรือ Deploy
