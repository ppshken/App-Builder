# ผลตรวจประสิทธิภาพสูตร — 14 พฤศจิกายน 2026

ตรวจ Source Code และทดสอบด้วย SQLite ในหน่วยความจำ/ฐานข้อมูล integration แยก ไม่แก้ข้อมูลหรือ Deploy Production ฐานข้อมูลจริงในเครื่องอ่านเฉพาะ metadata และจำนวนแถว จึงไม่ใช่ผลวัด VPS

## สาเหตุที่พบ

1. SELECT ที่ใช้ `[inspection_id] = [_THISROW].[inspection_id]` อ่าน projected table ไว้แล้ว แต่ยังวนทั้งตารางทุกแถวที่แสดง การนับและรวมค่าหลายสูตรจึงมีงานใกล้เคียงจำนวนแถวที่แสดง × จำนวนแถวต้นทาง × จำนวนสูตร การปลดเพดาน 10,000 แถวทำให้งานส่วนนี้ขยายได้มากขึ้น
2. การดึง `[ref].[field]` ใช้ Array.find หาแถวแม่ซ้ำ แม้โหลดข้อมูลแม่มาแล้ว
3. การเรียง/กรองด้วยคอลัมน์คำนวณ และการค้นหาที่เกี่ยวข้องกับ Ref/คอลัมน์คำนวณ ทำให้ API บางกรณีต้องคำนวณข้อมูลทั้งหมดก่อนแบ่งหน้า (`app/api/data/[table]/route.ts`)
4. SQLite และตัวประเมินสูตรทำงาน synchronous บน Node.js การคำนวณหนักจึงอาจหน่วงคำขออื่นใน process เดียวกัน ข้อนี้ตรวจจากโครงสร้างโค้ด ยังไม่ได้วัด concurrent load บน VPS

## การแก้ไข

- เพิ่ม lookup ภายใน expressionContext แต่ละครั้งสำหรับข้อมูลที่ผ่านสิทธิ์แล้ว จัดกลุ่มด้วยค่าคอลัมน์ จึงตรวจ predicate เฉพาะแถวที่อาจตรงกัน
- ใช้เมื่อเงื่อนไขแรกเป็น equality ระหว่างคอลัมน์ตรง ๆ กับ `_THISROW` เท่านั้น รวมถึง AND ที่เริ่มด้วย equality นี้ เงื่อนไข OR/NOT หรือสูตรที่อาจ throw ก่อน equality ยังประเมินแบบเดิม
- นำ lookup ไปใช้หา id ของ Ref ด้วย
- ยังประเมิน predicate จริงเพื่อรักษาความหมายของชนิดข้อมูล เก็บลำดับเดิม และ fallback เมื่อมี array/ข้อมูลไม่ครบ
- ไม่ cache ผลลัพธ์สูตร ไม่แชร์ lookup ข้ามคำขอ บัญชี แอป หรือการเขียนข้อมูล จึงไม่ทำให้ NOW/UNIQUEID หรือสิทธิ์ใช้ค่าค้าง

## ผลวัดจริง

สคริปต์ `node tests/formula-performance-benchmark.cjs` หลัง `npm test` ใช้ข้อมูลต้นทาง 12,000 แถว แสดง 150 แถว สูตรต่อแถว 3 สูตร (COUNT SELECT, SUM SELECT และ Ref) แต่ละกลุ่มมีลูก 10 แถว warm-up หนึ่งรอบก่อนวัด 5 รอบต่อแบบ เปรียบเทียบเปิด/ปิด lookup บนโค้ดเดียวกัน

| วิธี | มัธยฐาน | จำนวนอ่านตาราง |
| --- | ---: | ---: |
| วนตรวจแบบเดิม | 273.10 ms | 3 ครั้ง |
| ใช้ lookup | 37.99 ms | 3 ครั้ง |

เร็วขึ้นประมาณ 7.19 เท่าใน workload นี้ เป็นเวลาคำนวณบนเครื่อง local ไม่ใช่เวลารวม HTTP หรือการรับประกันความเร็ว Production ผลทุกรอบอยู่ใน benchmark.json

Regression ที่นับการอ่านค่าคอลัมน์ยืนยันลดจากการไล่ 1,800,000 แถว เหลือการสร้าง lookup ครั้งเดียว 12,000 แถวและตรวจกลุ่มที่ตรงกันรวม 1,500 แถว

## งานที่ยังมีต้นทุน

การอ่านและ normalize projected table ครั้งแรกยังต้องอ่านต้นทางทั้งหมดสำหรับ SELECT ที่ไม่ผูกแถวแม่โดยตรง ส่วน Related ที่ผูกแถวแม่ยังใช้ SQL Ref lookup ตามเดิม การกรอง/เรียงด้วยสูตรหนักยังอาจต้องคำนวณทั้งตาราง และ Automation ที่สร้าง expressionContext ใหม่หลายขั้นยังมีต้นทุนโหลด snapshot ใหม่ ไม่มีผลวัด CPU/RAM/network หรือ concurrent requests บน VPS ในงานนี้
