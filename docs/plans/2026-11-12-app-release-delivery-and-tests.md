# ลำดับพัฒนาและแผนทดสอบการอัปเดตแอป

วันที่: 12 พฤศจิกายน 2569

เอกสารสถาปัตยกรรม: [ออกแบบพัฒนาแอปควบคู่กับการใช้งานจริง](2026-11-12-app-release-architecture.md)

## ความคืบหน้าหลังเริ่มพัฒนา

ระยะ 1 พัฒนาและทดสอบแล้ว: มีตัวเปรียบเทียบแบบอ่านอย่างเดียวและหน้าผลกระทบในรีวิวเวอร์ชั่นแอป ดู [ผลพัฒนาและหลักฐานทดสอบระยะ 1](../features/2026-11-12-release-plan-phase-one.md)

ระยะ 2 พัฒนาและทดสอบรุ่นแรกแล้ว: เปิดพื้นที่พัฒนาโครงสร้างในสำเนาฐานข้อมูลแยก พร้อมจำกัดผลกระทบภายนอก ดู [ผลพัฒนาและหลักฐานทดสอบระยะ 2](../features/2026-11-12-development-workspace-phase-two.md)

ระยะ 3 รุ่นแรกพัฒนาและทดสอบแล้ว: ซ้อมการเพิ่มโครงสร้างที่รองรับกับสำเนาข้อมูลล่าสุด ตรวจค่าเดิม จำนวนแถว Ref และสูตร พร้อมอายุผลซ้อม ดู [ผลพัฒนาและข้อจำกัดระยะ 3](../features/2026-11-12-release-rehearsal-phase-three.md)

ต่อยอดระยะ 3 แล้ว: ปุ่มซ้อมใช้คิวถาวรและ process แยก พร้อมความคืบหน้า ยกเลิก และจัดการงานค้าง ดู [ผลพัฒนางานซ้อมเบื้องหลังและข้อจำกัด](../features/2026-11-12-rehearsal-background-jobs.md)

ระยะ 4 รุ่นแรกพัฒนาและทดสอบแล้ว: เผยแพร่เฉพาะโครงสร้างเพิ่มที่ผ่านเงื่อนไข มีสำรอง ธุรกรรม receipt ป้องกันซ้ำ และแจ้งเวอร์ชั่นใหม่โดยไม่รีโหลดฟอร์ม ดู [ผลพัฒนาระยะ 4 และข้อจำกัด](../features/2026-11-13-additive-publication.md)

ระยะ 5 ส่วนสูตร/เงื่อนไขพัฒนาและทดสอบแล้ว: รองรับคอลัมน์คำนวณ Required/ค่าเริ่มต้น/Valid_If ตรวจข้อมูลล่าสุดใน worker แยก และยืนยันสิทธิ์อัตโนมัติในหน้าเผยแพร่ ทดสอบจริงด้วย 6,000 แถว ดู [ผลพัฒนาเส้นทางเผยแพร่รุ่นใช้งาน](../features/2026-11-13-practical-schema-publication.md) ส่วนแปลงชนิด ลบ เปลี่ยนชื่อ และตารางร่วมยังถูกบล็อก ต้องพัฒนาต่อและทดสอบ Docker/Linux ก่อนสรุปความพร้อม Production

## ขอบเขตงานที่ทำในรอบออกแบบ

ตรวจระบบฉบับร่าง การเผยแพร่ การ Clone บริบทหลายแอป การตั้งค่าตารางร่วม การแปลงคอลัมน์ และการสำรองข้อมูลจากโค้ดจริง จัดทำแบบและเกณฑ์รับงานก่อนเปิดให้เปลี่ยนโครงสร้าง ไม่แก้ Source Code หรือข้อมูลจริงในรอบนี้

## ลำดับพัฒนา

### ระยะ 1 — เปรียบเทียบและแจ้งผลกระทบแบบอ่านอย่างเดียว

- สร้างตัวเปรียบเทียบจากฐานตั้งต้น แอปจริง และฉบับพัฒนา โดยไม่ผูกกับ HTTP หรือฐานข้อมูลในฟังก์ชันหลัก
- แยกการเปลี่ยนโครงสร้าง การตั้งค่า สิทธิ์ ตารางร่วม และความขัดแย้ง
- สร้างรายการขั้นตอนพร้อมลำดับการพึ่งพา การตรวจเงื่อนไข และเหตุผลที่บล็อก
- ต่อหน้ารีวิวเวอร์ชั่นแอปเดิม โดยไม่เปลี่ยนการเผยแพร่เดิมและไม่ปลดล็อกการแก้โครงสร้าง
- ตรวจขอบเขตแอปและสิทธิ์ทุกคำขอ ไม่เปิด endpoint สำหรับเผยแพร่โครงสร้างในระยะนี้

จุดเชื่อม: `lib/releases.ts`, `app/api/releases/route.ts`, `app/releases/page.tsx`, `lib/readiness.ts`, ตัววิเคราะห์สูตรและความสัมพันธ์เดิม

ไฟล์ใหม่ที่เสนอ: `lib/release-plan.ts` สำหรับวิเคราะห์ข้อมูลที่ส่งเข้ามา และ `tests/release-plan.test.cjs` สำหรับทดสอบแผน ไม่เพิ่ม Migration Engine ระหว่างทำเพียงตัวเปรียบเทียบ

เกณฑ์จบ: ผลคงที่แม้ลำดับแถวต่างกัน ตรวจการเปลี่ยนโดยไม่แก้ input และฐานข้อมูลจริง แสดงตาราง/คอลัมน์ที่เพิ่มหรือลบได้ครบ พร้อมบล็อกสิ่งที่ยังไม่รองรับ ไม่ใช้ชื่อแสดงเดาการเปลี่ยนชื่อ

### ระยะ 2 — พื้นที่พัฒนารองรับโครงสร้างแยกจริง

- เก็บสายกำเนิดและการจับคู่วัตถุของพื้นที่พัฒนาใหม่
- อนุญาตการเพิ่มตารางและคอลัมน์เฉพาะฐานข้อมูลแยกที่ยืนยันได้ ไม่ปลดข้อจำกัดร่างเก่าทั้งหมด
- ป้องกันการส่งออกจริง งานเบื้องหลัง และการเขียนไฟล์ข้ามพื้นที่
- รองรับข้อมูลทดลองและล้างพื้นที่ทดลองโดยมีการตรวจว่าข้อมูลจริงไม่เปลี่ยน
- เก็บนโยบายและอายุสำเนา รวมถึงผลกระทบจากการสำเนา SQLite ที่มีหลายแอป

จุดเชื่อม: `lib/draft-request.ts`, `lib/db.ts`, `lib/application-context.ts`, `lib/application-lifecycle.ts`, ตัวบันทึกไฟล์และตัวทำงานเบื้องหลัง

เกณฑ์จบ: ผู้พัฒนาสองพื้นที่เพิ่มชื่อคอลัมน์เดียวกันได้โดยไม่ชนกัน ผู้ใช้แอปจริงไม่เห็นโครงสร้างใหม่ และการทดสอบยืนยันว่าไม่มีอีเมล Push HTTP หรืองานจริงถูกส่งออก

### ระยะ 3 — ซ้อมอัปเดตโดยไม่แตะปลายทางจริง

- สร้างสำเนาข้อมูลล่าสุดสำหรับซ้อมและตรวจพื้นที่ปลายทางอย่างเข้มงวด
- ใช้แผนระบุชนิดคำสั่งที่อนุญาต ไม่รับ SQL จาก Client
- นำตัวตรวจสูตรและแปลงชนิดเดิมกลับมาใช้ในบริบทฐานข้อมูลซ้อม
- รายงานจำนวนข้อมูลก่อน/หลัง ความถูกต้องของ Ref ข้อจำกัด และระยะเวลา โดยไม่บันทึกค่าข้อมูลส่วนบุคคล
- บันทึกลายนิ้วมือแผนและผลซ้อม พร้อมตรวจว่างานหมดอายุเมื่อแผนเปลี่ยน

เกณฑ์จบ: ซ้อมผิดพลาดหรือถูกยกเลิกแล้วแอปจริงไม่เปลี่ยน ตรวจไฟล์และผลข้างเคียงร่วมกับฐานข้อมูล ไม่เรียกการตรวจโค้ดว่าการซ้อมผ่าน

### ระยะ 4 — เผยแพร่เฉพาะการเพิ่มโครงสร้างที่รองรับ

- เริ่มจากตารางของแอปเอง และคอลัมน์ที่ยอมรับค่าว่าง ไม่มีการลบ เปลี่ยนชนิด เปลี่ยน Key หรือแก้โครงสร้างตารางร่วม
- เพิ่มธุรกรรมและสถานะงานที่ป้องกันการเผยแพร่ซ้ำข้าม process ได้
- ตรวจสิทธิ์และโครงสร้างอีกครั้งก่อน commit เก็บสำรองและประวัติงาน
- กำหนดสิทธิ์ของตาราง/Action ใหม่จากผู้ดูแล ไม่เดาว่าทุกบทบาทควรได้สิทธิ์
- อัปเดตการตั้งค่าหลังโครงสร้างรองรับ และแจ้ง Runtime โดยไม่ทิ้งฟอร์มที่ผู้ใช้กรอกค้าง

เกณฑ์จบ: แถวจริงที่เพิ่มระหว่างพัฒนายังอยู่ครบ รหัสแอปและรหัสแถวไม่เปลี่ยน ข้อมูลทดลองไม่ถูกนำเข้า งานล้มเหลวไม่เผยแพร่การตั้งค่าเพียงครึ่งเดียว และคำขอเก่าถูกจัดการอย่างชัดเจน

### ระยะ 5 — แปลง ลบ เปลี่ยนชื่อ และตารางร่วม

- เปิดแต่ละชนิดงานแยกกันหลังมีหลักฐานการทดสอบและแผนกู้คืน
- เพิ่มการจับคู่เปลี่ยนชื่อจากสายกำเนิด แผนเติมข้อมูล และการตรวจ Unique/Key กับข้อมูลล่าสุด
- ตรวจผลกระทบทุกแอปที่เชื่อมตารางร่วม และล็อกงานที่ขัดแย้งกันโดยไม่พึ่ง process เดียว
- วัดเวลาบนข้อมูลใหญ่ กำหนดช่วงพักและวิธีแก้เมื่อถูกยกเลิกกลางงาน

เกณฑ์จบ: ไม่มีการเลือกใช้การคืนฐานข้อมูลทั้งระบบเพื่อย้อนงานของแอปเดียวโดยอัตโนมัติ และไม่เปิดงานเสี่ยงสูงโดยไม่มีการตรวจแผนจริง

## ข้อตกลงข้อมูลและ API ที่เสนอ

ใช้ `/api/releases` ตามรูปแบบเดิม เพิ่มข้อมูลรีวิวแบบอ่านอย่างเดียวก่อน โดยคงข้อมูลเดิมที่หน้าเก่าใช้ได้

- ผลเปรียบเทียบมี `plan_version`, `source_app_id`, `workspace_id`, `target_app_id`, ลายนิ้วมือฐานตั้งต้น/แอปจริง/พื้นที่พัฒนา และรายการ `operations`, `conflicts`, `blockers`
- ขั้นตอนแต่ละรายการมีรหัส ชนิดวัตถุ รหัสกำเนิด ชนิดคำสั่ง ระดับความเสี่ยง การพึ่งพา เงื่อนไขก่อน/หลัง และ `supported` ที่บอกความสามารถจริงของรุ่นนั้น
- API ซ้อมและเผยแพร่เป็นระยะถัดไป รับรหัสแผนและข้อมูลยืนยัน ไม่รับชุดคำสั่งจาก Client ไปทำทันที
- ใช้รหัสคำขอซ้ำที่ผูกกับแอป แผน ผู้กระทำ และชนิดงาน คำขอซ้ำคืนผลเดิมเมื่อทำสำเร็จแล้ว ไม่เริ่มทำรอบใหม่
- เผยแพร่พร้อมกันแผนเดียวกันต้อง commit ได้ครั้งเดียว แผนต่างกันแต่เปลี่ยนวัตถุเดียวกันต้องตรวจลายนิ้วมือใหม่
- ผลข้อผิดพลาดต้องแยกไม่มีสิทธิ์ แผนเปลี่ยน ปลายทางเปลี่ยน ยังไม่รองรับ ตรวจข้อมูลไม่ผ่าน หมดเวลา และต้องตรวจการกู้คืน ไม่ส่ง Stack Trace หรือข้อมูลแถวจริงให้ผู้ใช้ทั่วไป

โครงสร้างนี้เป็นแบบที่เสนอ ยังไม่มี API ใหม่ที่ใช้งานได้จากเอกสารนี้

แต่ละการทดสอบต้องมีผลจริงและหลักฐาน แยกการทดสอบฟังก์ชัน การทดสอบ API การทำงานพร้อมกัน และเบราว์เซอร์ ไม่ใช้ผล Build แทนผลทดสอบการรักษาข้อมูล

## ผลตรวจรอบออกแบบ

ทดสอบพฤติกรรมระบบเดิมด้วย Production Build ในฐานข้อมูลจำลองผ่านตัวรัน `scripts/integration.cjs` ไม่ใช้ฐานข้อมูลจริง

| ชุดทดสอบเดิม | ผลที่ได้จริง | หลักฐาน |
|---|---|---|
| ฉบับร่างและความพร้อมเผยแพร่ | ผ่าน: แยกข้อมูลร่าง เผยแพร่/ย้อนการตั้งค่า ตรวจรีวิวเก่า การเปลี่ยนพร้อมกัน สิทธิ์ และหน้า Builder | `.test-data/release-design-readiness.log`, process จบด้วยรหัส 0 |
| หลายแอป | ผ่าน: เพดานสิทธิ์ตารางร่วม ขอบเขตสูตร/Ref/Excel แท็บเก่า สมาชิก งานเบื้องหลัง และสลับแอปบนขนาด Desktop/Mobile | `.test-data/release-design-multiapp.log`, process จบด้วยรหัส 0 |

ผลเหล่านี้ยืนยันพฤติกรรมเดิมที่ใช้เป็นฐานออกแบบ ไม่ใช่หลักฐานว่าการเผยแพร่โครงสร้างใหม่ทำงานแล้ว

รายการที่ยังไม่ได้ทดสอบ: ตัวเปรียบเทียบใหม่ การสร้างแผนใหม่ พื้นที่พัฒนาโครงสร้าง การซ้อมอัปเดต การเผยแพร่โครงสร้าง การกู้คืนหลัง process หยุด และการทดสอบหนึ่งล้านแถว เพราะยังไม่ได้พัฒนาความสามารถเหล่านี้

## สิ่งที่ไม่ทำในระยะแรก

- ไม่ปลดข้อจำกัดใน `withDraftRequest` เพื่อให้เพิ่มโครงสร้างได้ทันที
- ไม่แทนฐานข้อมูลจริงด้วยฐานข้อมูลของ Clone
- ไม่รวมข้อมูลแถวทดลองเข้าแอปจริง
- ไม่ปรับสมาชิก รหัสผ่าน หรือเพดานสิทธิ์จากพื้นที่พัฒนา
- ไม่ส่ง Push อีเมล HTTP หรือรันงานจริงระหว่างซ้อม
- ไม่ Deploy หรือเปลี่ยน Production จากการอนุมัติให้ออกแบบ
