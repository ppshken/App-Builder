# เตรียม Deploy รุ่นปัจจุบันโดยไม่เปิดงานโครงสร้างที่ยังไม่พร้อม

> อัปเดต: รองรับเงื่อนไขคอลัมน์ ตรวจข้อมูลล่าสุดใน worker แยก และยืนยันสิทธิ์อัตโนมัติแล้ว ข้อจำกัด 2,000 แถว/ต้องปิดสิทธิ์อัตโนมัติในเอกสารระยะก่อนถูกแทนด้วย [ขั้นตอนเผยแพร่รุ่นใช้งาน](../features/2026-11-13-practical-schema-publication.md)

วันที่: 13 พฤศจิกายน 2569

## ขอบเขตรุ่นนี้

เก็บความสามารถระยะ 1–4 และคอลัมน์คำนวณระยะ 5 ส่วนแรกไว้ ส่วนเปลี่ยนชื่อ แปลงชนิด ลบโครงสร้าง และตารางร่วมยังไม่เปิดเผยแพร่ ไม่เพิ่มงานเหล่านี้ก่อน Deploy รอบเร่งด่วน

เพิ่มสวิตช์ `NOCODE_SCHEMA_PUBLICATION` ฝั่งเซิร์ฟเวอร์ ค่าเริ่มต้น `0` ปิดเฉพาะการเผยแพร่จากพื้นที่พัฒนาโครงสร้าง การใช้งานข้อมูลจริง ฉบับร่างการตั้งค่าแบบเดิม และการซ้อมยังใช้ได้ ต้องตั้งเป็น `1` จึงเผยแพร่โครงสร้างได้ และยังต้องผ่านสิทธิ์ ผลซ้อม และการยืนยันตามเดิม สวิตช์นี้ไม่ย้อนเวอร์ชั่นที่เผยแพร่สำเร็จแล้ว

เพื่อทดสอบบนฐานจำลอง ตัวรัน Integration กำหนด `1` อย่างชัดเจน ส่วนชุด `publicationdisabled` กำหนด `0` และพิสูจน์ว่าซ้อมผ่านแล้วก็ยังยิง API เผยแพร่ตรง ๆ ไม่ได้

## สิ่งที่ตรวจและหลักฐาน

| รายการ | หลักฐาน |
|---|---|
| หน่วยทดสอบรวม | `.test-data/predeploy-unit.log` |
| Production Build รวม worker | `.test-data/predeploy-build.log` |
| Compose แบบ HTTP, HTTPS และ Nginx พร้อมการบรรจุ worker | `.test-data/predeploy-config-final.json` |
| เผยแพร่คอลัมน์จริง/ธุรกรรม/คำขอซ้ำ | `.test-data/predeploy-publication.log` |
| เผยแพร่คอลัมน์คำนวณและตรวจข้อมูลล่าสุด | `.test-data/predeploy-formula.log` |
| สวิตช์ปิดการเผยแพร่และป้องกันเรียก API ข้าม UI | `.test-data/predeploy-disabled.log` |
| งานซ้อมเบื้องหลัง | `.test-data/predeploy-jobs.log` |

ตัวตรวจการติดตั้งเดิมล้มเหลวก่อนแก้เพราะคาดหวังคำสั่ง Build รุ่นเก่าและใช้เครื่องหมายพาธเฉพาะ Linux หลักฐาน `.test-data/predeploy-config-red.json` ปรับให้ตรวจคำสั่งสร้าง worker ตามจริง ตรวจว่า Dockerfile คัดลอก worker และไม่ใช้ artifact จากเครื่องผู้พัฒนา รวมถึงยืนยันว่าโหมด Nginx เปิดเฉพาะ `127.0.0.1:3001` และ proxy ในชุดไม่เริ่มจนกว่าจะเปิด profile

ผลตรวจ Compose เป็นการตรวจ configuration ไม่ใช่การเริ่ม Container จริง Docker daemon สำหรับ Linux ในเครื่องนี้ไม่พร้อม หลักฐาน `.test-data/predeploy-docker.log` จึงยังไม่ยืนยัน Linux Container, Nginx, TLS หรือประสิทธิภาพบน VPS รุ่นนี้ ไม่ได้ใช้ผลทดสอบ Container ในรายงานเก่ามาอ้างแทนรุ่นปัจจุบัน

## ผลตรวจรุ่นสุดท้าย

- Build ผ่าน และหน่วยทดสอบผ่าน 591 ข้อ ล้มเหลว 0 ข้อ ข้าม 7 ข้อสำหรับ POSIX
- ตัวตรวจ configuration ผ่าน 13 ข้อ อีก 1 รายการต้องตั้งค่าตามเซิร์ฟเวอร์จริง ไม่ใช่ผลยืนยันโดเมน/TLS
- API และเบราว์เซอร์บน Production Build ผ่านทั้งการเผยแพร่เดิม การเผยแพร่สูตร การบล็อกด้วยสวิตช์ งานซ้อมเบื้องหลัง Realtime และ PDF
- Realtime ตรวจการเพิ่ม/แก้/ลบข้ามผู้ใช้ ฟอร์มค้าง การเชื่อมต่อใหม่และเพิกถอนสิทธิ์ หลักฐาน `.test-data/predeploy-realtime.log`
- PDF ตรวจตารางลูก การแบ่งหน้า ตัวอย่าง บันทึก/โหลด สร้าง PDF และมือถือ หลักฐาน `.test-data/predeploy-pdf.log`
- ไม่ได้ Deploy และไม่ได้เปลี่ยนฐานข้อมูลจริง Docker/Linux รุ่นนี้ยังไม่ได้ทดสอบ runtime จึงคงสวิตช์เผยแพร่โครงสร้างเป็น 0 สำหรับรอบเร่งด่วน

## ขั้นตอนบนเซิร์ฟเวอร์ที่ใช้ Nginx เดิม

คำสั่งต่อไปนี้เป็นคู่มือ ยังไม่ได้รันกับ Production

1. ตรวจว่าไฟล์ใหม่ทั้งหมดของงานระยะ 1–5 ขึ้นเซิร์ฟเวอร์แล้ว รวม `lib/`, `app/components/` และ `scripts/build-rehearsal-worker.cjs` การมีเพียง diff ของไฟล์เดิมไม่พอ ใช้ `git status --short` ตรวจไฟล์ใหม่ก่อนส่งงาน ห้ามรวม `.env`, ฐานจริง หรือ uploads เข้าระบบเวอร์ชั่น
2. แก้ `.env.docker` เดิมเฉพาะค่าที่จำเป็น อย่าเขียนทับ credentials และตั้ง `NOCODE_SCHEMA_PUBLICATION=0` เก็บชื่อโครงการ Compose และ volume เดิม
3. บันทึกชื่อ/รหัส image เดิม และเก็บ image เดิมไว้สำหรับย้อนแอป ควรใช้ tag รุ่นที่ไม่ซ้ำ แทนการพึ่ง `latest`
4. ตรวจ configuration โดยไม่แสดงค่าลับ และ Build image ก่อนเปลี่ยน Container ที่กำลังใช้งาน:

```bash
docker compose --env-file .env.docker -f compose.yaml -f compose.nginx.yaml config --quiet
docker compose --env-file .env.docker -f compose.yaml -f compose.nginx.yaml build app
```

5. กำหนดช่วงพักสั้น ๆ และแจ้งผู้ใช้ให้บันทึกงานก่อน สำรอง volume ด้วยเครื่องมือเดิม คำสั่งนี้จะหยุดแอปชั่วคราวและเปิด Container เดิมกลับหลังสำรอง:

```bash
sh deploy/backup.sh .env.docker
```

สำรองนี้รวมฐาน SQLite และไฟล์ข้างเคียง ต้องตรวจว่าไฟล์สำรองสร้างสำเร็จ เก็บอีกชุดนอก VPS และยืนยันว่าใช้โครงการ/volume เดิมก่อนเริ่ม ห้ามใช้ `down -v` หรือเคลียร์ volume

6. เปลี่ยนเฉพาะแอป โดยไม่เริ่ม Caddy เพิ่มและไม่เปลี่ยน Nginx:

```bash
docker compose --env-file .env.docker -f compose.yaml -f compose.nginx.yaml up -d --no-deps --wait --wait-timeout 180 app
docker compose --env-file .env.docker -f compose.yaml -f compose.nginx.yaml ps
curl -fsS --max-time 10 http://127.0.0.1:3001/api/health
```

7. ทดสอบผ่านโดเมนจริง: Login เปิดรายการ/รายละเอียด บันทึกข้อมูลทดสอบที่แยกจากข้อมูลผู้ใช้ ตรวจรูป PDF และ realtime ตามฟีเจอร์ที่ใช้งาน ตรวจว่าหน้าเผยแพร่โครงสร้างแจ้งปิดไว้ และให้ผู้ใช้ทดลองก่อนจบช่วงพัก
8. ถ้า health ไม่ผ่าน ให้ตรวจ log และย้อนใช้ image เดิมที่เก็บไว้ก่อน ห้ามคืนฐานทั้งระบบอัตโนมัติ เพราะผู้ใช้อาจมีข้อมูลใหม่ ต้องแยกปัญหาแอปกับปัญหาฐานข้อมูลก่อนตัดสินใจกู้คืน

## หลัง Deploy รุ่นปัจจุบัน

ใช้ staging คนละ Compose project และคนละ volume ทดสอบการเผยแพร่โครงสร้างด้วย `NOCODE_SCHEMA_PUBLICATION=1` วัดช่วงล็อกและลองกู้คืนก่อนเปิดบน Production ส่วนงานเปลี่ยนชื่อ แปลงชนิด ลบ และตารางร่วมเป็นงานรอบถัดไป ไม่จำเป็นต่อการเปิดใช้รุ่นปัจจุบัน
