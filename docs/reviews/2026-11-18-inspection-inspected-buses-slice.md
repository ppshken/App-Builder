# ตรวจ View รถบัสที่ตรวจสภาพแล้ว

ตรวจวันที่ 18 พฤศจิกายน 2569 ในแอป Inspection EDIT เปิดฐานข้อมูลบนเครื่องพัฒนาด้วย `readonly: true` และ `fileMustExist: true` ไม่แก้การตั้งค่า ไม่เปลี่ยนข้อมูลจริง และไม่ Deploy

## การตั้งค่าที่พบ

- View: `view_90` ชื่อ รถบัสที่ตรวจสภาพแล้ว รูปแบบตาราง เรียงรหัสจากใหม่ไปเก่า
- ตาราง: `c_30ee7505_10_c_233e1e0b_19_cars`
- Slice: `slice_3` ชื่อ รถบัสที่ตรวจแล้ว
- เงื่อนไข: `ISNOTBLANK([last_inspection_id])`
- `last_inspection_id` เป็นคอลัมน์คำนวณชนิด Ref เลือกรายการตรวจล่าสุดด้วย Related, SELECT และ ORDERBY เฉพาะประเภทการตรวจ 1 หรือ 4
- View แสดงคะแนน เกรด ผู้ตรวจ วันตรวจ และข้อมูลรถหลายคอลัมน์

## ผลตรวจประสิทธิภาพ

`lib/slice-sql.ts` แปลงเงื่อนไขของคอลัมน์จริงที่รองรับเป็น SQL ได้ แต่ตั้งใจไม่แปลงคอลัมน์คำนวณ เงื่อนไขนี้จึงได้แผน SQL เป็นค่าว่าง ไม่ใช่ข้อผิดพลาดของชื่อ Slice หรือการเชื่อมตาราง

ใน `app/api/data/[table]/route.ts` จุดเลือกเส้นทาง `fast` ต้องมีแผน Slice ที่รองรับก่อน เมื่อไม่มีแผน จึงเรียก `readRows` คำนวณทุกแถว แล้วกรอง Slice เติม Label เรียงลำดับ และแบ่งหน้าในหน่วยความจำภายหลัง

ผลจำลองเส้นทางอ่านจริงด้วยบริบทเจ้าของจำลอง:

| งาน | ผล |
| --- | ---: |
| รถที่อ่านก่อนกรอง | 1,671 คัน |
| รถที่ผ่านเงื่อนไข | 267 คัน |
| คำนวณข้อมูลรถทุกคอลัมน์ | 2,334 มิลลิวินาที |
| ตรวจเงื่อนไข Slice | 548 มิลลิวินาที |
| เติมชื่อข้อมูล Ref | 7 มิลลิวินาที |
| แถวที่มีข้อผิดพลาดการคำนวณ | 0 |

หลักฐาน `.test-data/inspection-slice-profile.log` เป็นเวลาของโมดูลอ่านข้อมูลบนเครื่องพัฒนา ไม่ใช่การวัด HTTP หรือเบราว์เซอร์บน VPS และไม่รวมผลต่างจากสิทธิ์ระดับแถวของผู้ใช้จริง

ทดลองเฉพาะในสคริปต์ทดสอบให้คำนวณคอลัมน์สำหรับเงื่อนไขก่อน ได้รถ 267 คันเท่ากัน ใช้ประมาณ 835 มิลลิวินาที โดยยังไม่คำนวณค่าทั้งหมดของหน้าจอ

อีกการทดลองแบ่งงานเป็นกรองก่อนแล้วคำนวณเต็มเฉพาะ 25 คันของหน้าแรก ใช้กรอง 775 มิลลิวินาที เตรียมหน้าแรก 1,414 มิลลิวินาที รวม 2,189 มิลลิวินาที เปรียบเทียบข้อมูลหน้าแรกทุกคอลัมน์ด้วยแฮชแล้วตรงกับเส้นทางเดิม หลักฐาน `.test-data/inspection-slice-prototype.log` ยังไม่ได้ใส่แนวทางทดลองนี้ในโค้ดระบบ ตัวเลขยืนยันว่าการแบ่งงานอย่างเดียวช่วยได้บางส่วน แต่ยังต้องลดการโหลด Ref ที่เกิดภายในเครื่องอ่านแถวด้วย

## ความหมายของเงื่อนไข

เงื่อนไขปัจจุบันหมายถึงมีรายการตรวจล่าสุดที่ตรงประเภท 1 หรือ 4 ไม่ได้บังคับสถานะเสร็จแล้ว นอกจากนี้ไม่ได้หมายถึงการตรวจล่าสุดทุกประเภท เพราะสูตร Ref เลือกเฉพาะสองประเภทนี้

นับสถานะของรายการตรวจที่ Ref ล่าสุดชี้ถึง พบ:

| สถานะ | จำนวนรถ |
| --- | ---: |
| เปิดรายการตรวจสภาพ | 2 |
| ตรวจเสร็จ รอรับใบสั่งงาน | 10 |
| รับใบสั่งงาน เรียบร้อย | 255 |

ดังนั้นชื่อหน้าอาจสื่อว่าเสร็จแล้ว ขณะที่เงื่อนไขยังรับรถที่เปิดรายการค้างอยู่สองคัน นี่เป็นข้อสังเกตทางธุรกิจ ไม่สรุปว่าผิดจนกว่าจะยืนยันนิยามของหน้า ไม่เปลี่ยนเงื่อนไขให้ผู้ใช้โดยอัตโนมัติ

## ลำดับที่แนะนำ

1. แยกแผนคำนวณเงื่อนไข Slice ออกจากคอลัมน์ที่ใช้แสดง กรองสิทธิ์และเงื่อนไขให้ครบก่อนคำนวณข้อมูลหน้า 25 รายการ
2. ลดการอ่าน Ref ตามรหัสที่ต้องใช้ในเครื่องอ่านแถว `readRows` โดยรักษาการคำนวณตามบริบทแถว ฟอร์ม และสูตรที่ต้องอ่านทั้งตาราง งานนี้คนละเส้นทางกับ `/api/expression-data` ที่ปรับรอบก่อน
3. หากต้องการให้หน้าแสดงเฉพาะงานตรวจเสร็จ จึงเพิ่มเงื่อนไขสถานะตามนิยามที่ยืนยัน ไม่ใช้การเปลี่ยนชื่อหรือเปลี่ยนสูตรเพื่อกลบปัญหาความช้า
4. ต้องทดสอบจำนวนรวม หน้าแรก/หน้าถัดไป ค้นหา เรียงคอลัมน์คำนวณ Group By สิทธิ์ระดับแถว และข้อมูลที่เปลี่ยนสถานะ ก่อนใช้แผนอ่านใหม่จริง
