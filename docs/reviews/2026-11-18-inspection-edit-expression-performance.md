# ผลตรวจความช้าของสูตรในแอป Inspection EDIT

ตรวจวันที่ 18 พฤศจิกายน 2569 บนเครื่องพัฒนา โดยเปิดฐานข้อมูลด้วย `readonly: true` และ `fileMustExist: true` ไม่แก้ข้อมูลจริง ไม่เปลี่ยนโค้ดระบบ และไม่เผยแพร่ระบบ

## อาการและวิธีตรวจ

ผู้ใช้พบคำขอ `/api/expression-data` ของตาราง `c_30ee7505_10_c_233e1e0b_19_cars` ใช้เวลา 12.7 วินาที โดยระบุ `display=1` และรหัสรถ 25 แถว แต่ไม่ได้ระบุ `fields`

คอมไพล์ `lib/expression-context.ts` และโมดูลที่เกี่ยวข้องไปยังพื้นที่ทดสอบ จากนั้นเรียกเส้นทางเตรียมข้อมูลสูตรเดียวกับคำขอ โดยใช้ขอบเขตแอปจากเจ้าของตารางและบริบทเจ้าของจำลอง ใช้เฉพาะการอ่านฐานข้อมูล บันทึกเพียงจำนวนและเวลา ไม่บันทึกค่าข้อมูลของแต่ละแถวหรือข้อมูลบัญชีจริง

นี่เป็นการวัดการทำงานของเครื่องคำนวณจริงกับฐานข้อมูลบนเครื่องพัฒนา ไม่ใช่การยิงคำขอ HTTP ของผู้ใช้เดิม และไม่ได้วัดเครือข่ายหรือการแสดงผลบนเบราว์เซอร์ สิทธิ์ระดับแถวของผู้ใช้จริงอาจทำให้เวลาแตกต่างออกไป

ตัวเลขแถวสะสมรวมการโหลดซ้ำ ไม่ใช่จำนวนแถวที่ไม่ซ้ำ และจำนวนครั้งที่โหลดไม่ใช่จำนวน SQL ทั้งหมดของคำขอ การวัดแต่ละกรณีทำหนึ่งครั้ง ใช้อธิบายต้นเหตุ ยังไม่ใช่ค่าประสิทธิภาพรับประกันหรือเปอร์เซ็นไทล์

ตารางรถมี 1,671 แถว 23 คอลัมน์ โดยเป็นคอลัมน์คำนวณ 17 คอลัมน์ ผลลัพธ์กรณีเต็มมีข้อมูลการตรวจสภาพ 352 แถว และรายการตรวจลูก 16,022 แถว ข้อมูลการตรวจสภาพในผลลัพธ์ไม่มีขอบเขตจำกัดเฉพาะรถ 25 แถว

## สาเหตุที่ยืนยันได้

1. `app/api/expression-data/route.ts:22` เมื่อไม่มี `fields` แม้เป็น `display=1` ก็รวบรวมทุกชนิดสูตรของคอลัมน์ที่ไม่ใช่ List ไม่ได้จำกัดเฉพาะความต้องการของหน้าจอ และยังรวมสูตร Action และ Slice เพิ่มในส่วนถัดไป
2. คอลัมน์ `last_inspection_id` เลือกรายการตรวจล่าสุดด้วย Related, SELECT และ ORDERBY จากนั้นคอลัมน์คะแนนและเกรดหลายคอลัมน์ดึงข้อมูลต่อผ่าน Ref ของคอลัมน์นี้
3. `lib/expression-context.ts:135` ถึง `:136` โหลดตารางปลายทางแยกตามชุดคอลัมน์ที่แต่ละสูตรต้องใช้ การดึงคะแนนผ่าน Ref จึงเตรียมการตรวจสภาพทั่วตารางและคำนวณรายการลูกต่อ เกิดงานซ้ำสะสมจำนวนมาก
4. `lib/expression-context.ts:57` คำนวณสูตรของทุกแถวที่โหลดในแต่ละชุด การส่ง `related_parent_ids` จำกัด Related บางเส้นทาง แต่ไม่ได้จำกัดการโหลดปลายทางของ Ref ทุกเส้นทางให้อยู่ในรถ 25 แถว

การคำนวณสูตรข้ามตารางและการเตรียมข้อมูลเกินขอบเขตเป็นต้นเหตุที่วัดได้ ไม่ใช่ปัญหาจากจำนวนรถ 1,671 คันเพียงอย่างเดียว และยังไม่มีหลักฐานว่าขาดดัชนีเป็นสาเหตุหลัก

## แนวทางแก้ตามลำดับ

1. ส่งและใช้ชุดคอลัมน์ที่หน้าจอต้องใช้จริง พร้อมติดตามสูตรที่จำเป็นต่อการแสดงผล เงื่อนไข Action การกรอง และสิทธิ์ให้ครบ ห้ามตัดสูตรที่มีผลต่อการทำงานเพียงเพื่อให้เร็วขึ้น
2. รวมแผนความต้องการคอลัมน์ของตารางเดียวกันก่อนโหลด และใช้ผลคำนวณร่วมกันภายในคำขอ ลดการคำนวณคะแนนและเกรดชุดเดิมซ้ำ
3. จำกัดการอ่าน Ref ด้วยรหัสปลายทางที่เกี่ยวข้องกับแถวรถที่แสดง จากนั้นอ่านรายการลูกเฉพาะรายการตรวจเหล่านั้น ต้องมีทางถอยสำหรับสูตรที่ต้องคำนวณทั้งตารางจริง
4. เพิ่มการทดสอบผลลัพธ์เทียบก่อนและหลัง ทั้งคะแนน เกรด รายการตรวจล่าสุด กรณีไม่มีประวัติ หลาย Ref ผู้ใช้ต่างสิทธิ์ และข้อมูลที่เพิ่มหรือเปลี่ยนสถานะ

ไม่แนะนำจำกัดจำนวน Ref หรือรายการลูกไว้ 500 แถว เพราะอาจทำให้คะแนนและข้อมูลหาย และไม่แนะนำให้ผู้ใช้ลบคอลัมน์คำนวณเพื่อแก้อาการนี้

## สถานะ

ยืนยันและจำลองต้นเหตุได้แล้ว ต่อมาผู้ใช้อนุมัติให้แก้ไข โดยดำเนินการลดงานซ้ำภายในคำขอก่อน รายละเอียดด้านล่าง ไม่แก้สูตรของแอปหรือฐานข้อมูลจริง

## การแก้ไขหลังได้รับอนุมัติ

- `lib/expression-context.ts` รวมแคชตามตารางและขอบเขตแถวเดียวกัน แทนการแยกแต่ละชุดคอลัมน์ และอ่านจากผลเดิมได้เมื่อมีทุกคอลัมน์ที่ต้องการครบแล้ว รวมทั้งคอลัมน์ประกอบ Label และ Ref
- เมื่อจำเป็นต้องโหลดคอลัมน์เพิ่ม รวมผลกับคอลัมน์เดิมตามรหัสแถว เก็บภายในคำขอเท่านั้น ไม่แบ่งปันข้อมูลระหว่างผู้ใช้
- จำกัดจำนวนขอบเขตไว้ 1,024 รายการและจำนวนแถวสะสมในแคช Related ไว้ 20,000 แถวเช่นเดิม เพื่อหลีกเลี่ยงการขับข้อมูลของแม่ 352 แถวออกก่อนคำนวณคะแนนคอลัมน์ถัดไป ขีดจำกัดนี้เป็นการพักข้อมูลเพื่อประหยัดงาน ไม่ใช่การตัดข้อมูลผลลัพธ์
- ยังคงตรวจสิทธิ์ก่อนใช้แคช แยกแถวแม่ ช่อง Ref และแถวที่ยังไม่ผูกแม่ รักษาการตรวจสูตรวนซ้ำ และตรวจเพดานรหัสแม่ 500 รายการก่อนอ่านแคชด้วย
- ไม่แก้เส้นทาง Action หรือสูตรคะแนน ไม่ลดจำนวนแถวและคอลัมน์ที่ส่งกลับ รอบนี้ยังไม่เปลี่ยนเป็นแผนโหลด Ref เฉพาะรหัสปลายทาง เพื่อจำกัดความเสี่ยงต่อสูตรที่ต้องใช้ทั้งตาราง

## การทดสอบถดถอย

- เพิ่มกรณีแม่ 350 แถวและการขอคอลัมน์จำนวน/น้ำหนักสลับกัน เดิมโหลด 1,400 ครั้งและไม่ผ่านข้อกำหนดไม่เกิน 700 ครั้ง หลักฐาน `.test-data/inspection-projection-red.log`
- เพิ่มกรณีเปลี่ยนจาก Related เป็นการอ่านตารางปกติ ต้องยังมี Label ถูกต้อง กรณีเพดานรหัสแม่ และคำขอใหม่ต้องเห็นค่าที่เปลี่ยน
- ทดสอบการขับแคชเก่าออกจริงด้วยขอบเขต 1,100 รายการ แทน 300 รายการ เพื่อทดสอบให้เกินเพดานใหม่ 1,024 รายการ โดยยังคงยืนยันว่าต้องอ่านใหม่หลังถูกขับออก
- ชุดทดสอบรวมรุ่นสุดท้าย 657 ข้อ ผ่าน 650 ข้อ ข้าม 7 ข้อ ไม่พบข้อที่ล้มเหลว หลักฐาน `.test-data/inspection-projection-unit-final.log`
- การทดสอบที่เกี่ยวข้องกับ Related, สิทธิ์ระดับแถว, ORDERBY และสูตรรวมก่อนเก็บรายละเอียดรอบสุดท้าย ผ่าน 37 ข้อ หลักฐาน `.test-data/inspection-projection-regression.log`
- Build สำหรับ Production ของรุ่นสุดท้ายผ่าน รหัสจบงาน 0 โดยใช้ฐานข้อมูล Build แยก หลักฐาน `.test-data/inspection-projection-build-final.log` รอบแรกหยุดเพราะคำเตือนความปลอดภัยของ Next.js รุ่นเดิม จึงรันซ้ำ ไม่ได้เปลี่ยนแพ็กเกจ
- การทดสอบ Related ผ่าน API และเบราว์เซอร์กับ Production Build และฐานข้อมูลทดสอบแยกผ่าน รหัสจบงาน 0 หลักฐาน `.test-data/inspection-projection-related-api.log` ครอบคลุมสูตร Related, การดึงผ่าน Ref และ Action ที่ใช้บริบทแถวเดิม

## ข้อจำกัดที่ยังเหลือ

ข้อมูลตอบกลับยังประมาณ 3 MB และยังมีการเตรียมคะแนนข้ามตารางมากกว่าข้อมูลเฉพาะหน้าจอ การลดขนาดข้อมูลด้วยแผนโหลดตามรหัส Ref เป็นงานต่อยอดแยกจากการลดงานซ้ำรอบนี้ ต้องทดสอบสูตรที่จำเป็นต้องอ่านทั้งตารางก่อน ไม่ได้เปลี่ยน Production หรือ Deploy
