# ผลทดสอบการแปลงชนิดข้อมูล

วันที่ตรวจ: 18 พฤศจิกายน 2569

ใช้ฐานข้อมูลทดสอบที่สร้างใหม่และข้อมูลสมมติทั้งหมด ทดสอบผ่าน HTTP และเบราว์เซอร์บน Build ปัจจุบัน ไม่มีการเปลี่ยนฐานข้อมูลจริง ไม่มีการ Deploy และยังไม่แก้ Source Code

## สรุปผล

- ชุดทดสอบระดับฟังก์ชันเดิมผ่าน 16 ข้อ
- ชุดทดสอบ HTTP/เบราว์เซอร์เดิมผ่าน 3 ชุด: การแปลงทั่วไป, Color → Enum ของตารางร่วม และการแก้ต้นทาง/รีเจนตารางร่วม
- ตารางกรณีทดสอบเพิ่มเติม 24 กรณี ผ่านตามผลที่คาด 23 กรณี พบไม่ตรงตามที่คาด 1 กรณี คือการแปลงเป็น User ที่ไม่มีอยู่จริง
- ทดสอบเพิ่มเติมด้านบทบาทรายแอป เทียบกับบทบาทเดิม และเงื่อนไขรายการลูก พบปัญหายืนยันได้อีก 2 เรื่อง
- รวมข้อค้นพบยืนยันได้ 3 เรื่อง: P1 จำนวน 1 เรื่อง และ P2 จำนวน 2 เรื่อง

ผลว่า “ผ่าน” ในรายงานนี้หมายถึงกรณีที่ทดสอบ ไม่ใช่การรับรองว่าทุกคู่ชนิดข้อมูลหรือทุกแอปไม่มีปัญหา

## CONV-001 — ไม่ตรวจคอลัมน์ที่ถูกใช้ในสิทธิ์ระดับแถวของบทบาทรายแอป

สถานะ: ยืนยันบัคด้วยการใช้งานจริง

ระดับ: P1 · ความมั่นใจสูง

ขั้นตอนทำซ้ำ:

1. สร้างตารางที่มีคอลัมน์ Text และข้อมูล `true`, `false`
2. สร้างบทบาทรายแอปที่อ่านตารางได้ และกำหนดเงื่อนไขอ่าน `[value] = 1`
3. ให้บัญชีทดสอบใช้บทบาทนี้ ก่อนแปลงอ่านข้อมูลได้ 0 แถว
4. Owner ตรวจและแปลงคอลัมน์จาก Text เป็น Yes/No
5. ผลตรวจแจ้งว่าแปลงได้ ไม่มีปัญหา และยืนยันแปลงสำเร็จ
6. บัญชีเดิมอ่านข้อมูลใหม่ พบว่ามองเห็น 1 แถว ทั้งที่ไม่ได้แก้สูตรสิทธิ์

ผลคาดหวัง: การแปลงคอลัมน์ที่ถูกใช้ในเงื่อนไขสิทธิ์รายแอปต้องตรวจผลกระทบหรือบล็อกให้จัดการเงื่อนไขก่อน เหมือนการตรวจบทบาทเดิม

ผลจริง: บทบาทรายแอปไม่ถูกตรวจด้วยนโยบายเดียวกัน ทำให้การแปลงโดย Owner เปลี่ยนขอบเขตข้อมูลที่สมาชิกมองเห็นโดยไม่มีคำเตือนเรื่องสิทธิ์

ทดสอบเทียบ: ใช้สูตรเดียวกันกับบทบาทแบบเดิม ผลตรวจถูกปฏิเสธด้วยข้อความ “คอลัมน์นี้ใช้ในกฎสิทธิ์ระดับแถว…” จึงยืนยันความไม่สอดคล้องระหว่างกลไกสิทธิ์สองแบบได้

สาเหตุที่ยืนยันได้:

- `lib/column-conversion.ts:87` ตรวจเฉพาะ `_role_row_rules`
- บทบาทรายแอปเก็บเงื่อนไขใน `_application_role_rows` ตาม `lib/application-roles.ts:52`
- `lib/column-conversion.ts:30` ยังไม่รวมเงื่อนไขบทบาทรายแอปในลายนิ้วมือของแผนแปลงด้วย จุดลายนิ้วมือนี้เป็นความเสี่ยงประกอบจากโค้ด ยังไม่ได้จำลองการแก้บทบาทระหว่าง Preview กับ Apply ในรอบนี้

หลักฐาน: `artifacts/conversion-exploratory-2026-11-18/evidence.json` ส่วน `findings.appRole` ระบุจำนวนก่อน/หลัง สูตรที่ยังเหมือนเดิม และผลปฏิเสธของบทบาทเดิม

แนวทางแก้: ตรวจเงื่อนไขรายแอปที่อ้างอิงคอลัมน์ รวมเงื่อนไขที่เกี่ยวข้องในลายนิ้วมือแผน และคงขอบเขตการอ่านข้อมูลของแต่ละแอป หากกระทบสิทธิ์แอปอื่นควรแจ้งผลกระทบโดยไม่เปิดเผยแถวหรือข้อมูลส่วนตัวของแอปนั้น

การทดสอบถดถอยที่ต้องเพิ่ม: บทบาทเดิม/รายแอป สิทธิ์อ่าน/เพิ่ม/แก้ไข/ลบ ตารางร่วม และบทบาทเปลี่ยนหลัง Preview ต้องไม่ใช้ผลตรวจเก่ายืนยัน

## CONV-002 — แปลงเป็น User ผ่านได้โดยไม่ตรวจผู้ใช้ที่มีสิทธิ์เข้าแอป

สถานะ: ยืนยันบัคด้วยการใช้งานจริง

ระดับ: P2 · ความมั่นใจสูง

ขั้นตอนทำซ้ำ:

1. สร้างคอลัมน์ Text ใส่ `999999` โดยไม่มีผู้ใช้รหัสนี้ในฐานข้อมูลทดสอบ
2. เลือกแปลงคอลัมน์เป็น User แล้วตรวจการแปลง
3. ผลตรวจแสดง “พร้อมแปลงข้อมูล” จำนวน 1 แถว พบปัญหา 0 จุด
4. ยืนยันแปลงแล้วข้อมูล User ที่อ้างถึงรหัสซึ่งไม่มีอยู่จริงถูกเก็บได้
5. ทดลองเพิ่มข้อมูล `999999` ผ่าน API บันทึกแถวปกติ ได้ HTTP 400 พร้อมข้อความว่าต้องเลือกผู้ใช้ที่เปิดใช้งานและมีสิทธิ์เข้าแอป

ผลคาดหวัง: Preview และ Apply ต้องตรวจว่าผู้ใช้นั้นมีอยู่ เปิดใช้งาน และมีสิทธิ์เข้าแอป เช่นเดียวกับการกรอกฟอร์ม

สาเหตุที่ยืนยันได้:

- `lib/column-conversion.ts:61` ตรวจรูปแบบตัวเลขผ่านตัวแปลงค่า
- `lib/column-conversion.ts:137` ตัวตรวจแถวระหว่างแปลงยังไม่เรียกการตรวจสมาชิก User แบบเส้นทางบันทึกปกติ
- `lib/permissions.ts:46` เส้นทางบันทึกปกติเรียก `assertUserFields`
- `lib/user-fields.ts:11` ตรวจรายชื่อผู้ใช้ที่เปิดใช้งานและมีสิทธิ์เข้าแอป

หลักฐาน: `evidence.json` ส่วน `findings.user` และ `artifacts/conversion-exploratory-2026-11-18/invalid-user-preview.png`

ผลกระทบ: เก็บการอ้างอิงผู้ใช้ที่เลือกใช้งานจริงไม่ได้ อาจกระทบการแสดงชื่อ การมอบหมายงาน หรือการส่งแจ้งเตือน ทั้งสามผลกระทบปลายทางยังไม่ได้ทดสอบต่อในรอบนี้

แนวทางแก้: ใช้ข้อกำหนดสมาชิก User เดียวกับการบันทึกปกติในบริบทแอปที่กำลังแปลง ตรวจซ้ำก่อน Apply ไม่ตรวจแค่ชนิดและขอบเขตตัวเลข

การทดสอบถดถอยที่ต้องเพิ่ม: ผู้ใช้ถูกต้อง ไม่มีอยู่จริง ปิดใช้งาน ไม่มีสิทธิ์เข้าแอป ค่าว่าง และสิทธิ์ผู้ใช้เปลี่ยนระหว่างตรวจและยืนยัน

## CONV-003 — เปลี่ยนปลายทาง Ref แล้วไม่ตรวจจำนวนลูกตามเงื่อนไขแม่ใหม่

สถานะ: ยืนยันบัคด้วยการใช้งานจริง

ระดับ: P2 · ความมั่นใจสูง

ขั้นตอนทำซ้ำ:

1. สร้างแม่เดิมที่มีค่า `expected=1` และแม่ใหม่ที่มีค่า `expected=2`
2. สร้างลูกหนึ่งแถว อ้างอิงแม่เดิม แล้วเปิด Is a part of พร้อมเงื่อนไข `COUNT([_THIS]) = [expected]`
3. แปลงคอลัมน์ Ref ให้ชี้แม่ใหม่ โดยจับคู่ด้วย ID
4. ระบบตรวจผ่านและแปลงได้ ลูกย้ายไปอ้างอิงแม่ใหม่ครบ แต่มีเพียง 1 แถว ขณะที่เงื่อนไขต้องการ 2 แถว
5. ทดลองบันทึกแม่ใหม่ผ่านฟอร์ม/API ปกติ ได้ HTTP 400 เพราะรายการลูกไม่ผ่าน Valid_If

ผลคาดหวัง: Preview ต้องตรวจเงื่อนไขรายการลูกกับแถวแม่ที่ได้รับผลกระทบหลังแปลง หากไม่ผ่านต้องไม่อนุญาตให้ Apply

สาเหตุที่ยืนยันได้:

- `lib/column-conversion.ts:150` ตรวจความถูกต้องของโครงสร้างสูตรด้วย `assertPartSchema`
- `lib/column-conversion.ts:137` ตรวจค่าระดับแถว แต่ยังไม่ตรวจจำนวนลูกในบริบทแม่แบบการบันทึกปกติ
- `lib/part-of-records.ts:19` เส้นทางบันทึกปกติตรวจด้วย `assertParentParts`
- ตรวจหลังแปลงแล้ว `is_part_of=1` และสูตรเดิมยังอยู่ จึงเป็นการขาดการตรวจข้อมูล ไม่ใช่กรณีสูตรหรือการตั้งค่าถูกปิดทิ้ง

หลักฐาน: `evidence.json` ส่วน `findings.part` มีผล Preview ค่าการตั้งค่าหลังแปลง จำนวนลูก 1 แถว และข้อผิดพลาดจากการบันทึกปกติ

แนวทางแก้: ตรวจแม่เดิมและแม่ปลายทางที่ได้รับผลกระทบในสำเนาแปลง ใช้ตัวตรวจเงื่อนไขรายการลูกร่วมกับระบบบันทึก และย้อนธุรกรรมหากตรวจรอบสุดท้ายไม่ผ่าน

การทดสอบถดถอยที่ต้องเพิ่ม: เปลี่ยนปลายทาง Ref จับคู่ ID/Key รายการลูกบังคับกรอก Valid_If สูตรอ้างคอลัมน์แม่ และจำนวนลูกเปลี่ยนหลัง Preview

## กรณีทั่วไปที่ผ่าน

- Text → Decimal รักษาค่าว่างและศูนย์ ปฏิเสธเลขละเอียดเกินขอบเขตและเลขมีตัวคั่นหลักพัน
- Text → EnumList รองรับค่าเดี่ยว รายการ JSON และค่าว่าง ไม่ทิ้งสมาชิก List เพื่อฝืนแปลงเป็นตัวเลขเดี่ยว
- Text → Yes/No รองรับข้อความไทยและปฏิเสธค่าที่ตีความไม่ได้
- Date/DateTime/Time คงเขตเวลาไทย รวมกรณี UTC ที่ข้ามวัน และแจ้งเตือนเมื่อทิ้งส่วนวันที่หรือเวลา
- Phone, Email, URL, Price, Percent และ Rating ตรวจรูปแบบ/ขอบเขตตามกรณีที่ลอง
- Ref จับคู่ Key และสร้าง Inline การคัดลอกคงคอลัมน์เดิม และการแปลงคง ID/ประวัติเลขรัน
- Preview ไม่เปลี่ยนข้อมูลจริง กรณีค่าที่แปลงไม่ได้ยังคงข้อมูลและโครงสร้างเดิม
- มีการสำรองก่อนแปลงจริง ผลตรวจเก่าเมื่อข้อมูลเปลี่ยนถูกปฏิเสธ และไม่ใช้ Token เดิมซ้ำ
- Color → Enum ของตารางที่แชร์ไปแอปอื่นผ่าน และฝั่งแอปปลายทางรีเจนได้
- การป้องกัน SQL View, Trigger และดัชนีนอกระบบยังผ่านชุดทดสอบระดับฟังก์ชัน

## ขอบเขตที่ยังไม่ได้ทดสอบ

ยังไม่ได้ทดสอบทุกคู่ชนิดข้อมูล ฐานข้อมูลหลายล้านแถว การแปลงพร้อมกันหลาย Process การกู้คืนไฟล์สำรองจริง การเปลี่ยนสมาชิก User ระหว่าง Preview/Apply และ iPhone จริง ผลรอบนี้จึงยังใช้รับรองการแปลงทุกกรณีบน Production ไม่ได้

## ลำดับแก้ไขที่แนะนำ

1. CONV-001 ตรวจบทบาทรายแอปและผลต่อสิทธิ์ ก่อนใช้งานการแปลงกับคอลัมน์ที่เกี่ยวกับเงื่อนไขสิทธิ์
2. CONV-002 ตรวจสมาชิก User ให้ตรงกับการบันทึกปกติ
3. CONV-003 ตรวจเงื่อนไขรายการลูกเมื่อเปลี่ยน Ref

ยังไม่มีการแก้ไขสามประเด็นนี้ในรอบตรวจสอบ
