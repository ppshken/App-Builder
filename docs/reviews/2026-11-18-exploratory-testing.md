# ผลทดลองใช้งานระบบเพื่อหาจุดเสี่ยง

วันที่ตรวจ: 18 พฤศจิกายน 2569

## วิธีตรวจและขอบเขต

เปิดใช้งานผ่านเบราว์เซอร์จริงบน Build สำหรับใช้งานจริงของโครงการ ใช้ฐานข้อมูลทดสอบที่สร้างใหม่และข้อมูลสมมติทั้งหมด ไม่เชื่อมฐานข้อมูลจริง ไม่เปลี่ยน Source Code ไม่ Deploy และไม่ส่งแจ้งเตือนไปยังผู้ใช้จริง

ทดสอบ Desktop ขนาด 1440 × 1000 และจำลองมือถือขนาด 390 × 844 ผ่าน Chromium/Edge การจำลองนี้ไม่ใช่การทดสอบ Safari หรือ iPhone จริง

เครื่องมือเบราว์เซอร์ในแอปไม่มีเครื่องมือควบคุมในรอบนี้ จึงใช้ Playwright ที่ติดตั้งอยู่ในโครงการ ไม่ติดตั้ง Dependency เพิ่ม

ทดลองกดใช้งานแบบสำรวจทีละขั้น ตรวจสถานะหน้าจอ ข้อมูลที่บันทึก และภาพหน้าจอ ร่วมกับรันชุดทดสอบเดิมที่เกี่ยวข้องแยกฐานข้อมูลกัน

## ประเด็นที่ควรจัดการก่อน

### EXP-003 — ลองบันทึกใหม่หลังคำตอบจากเซิร์ฟเวอร์สูญหาย สามารถสร้างข้อมูลซ้ำ

ประเภท: ความเสี่ยงจากการออกแบบที่ยืนยันพฤติกรรมได้ขณะใช้งานจริง

ความสำคัญที่แนะนำ: P1 สำหรับระบบที่ข้อมูลซ้ำส่งผลต่อขั้นตอนธุรกิจ

ความมั่นใจ: สูง เฉพาะเส้นทางสร้างแถวธรรมดาที่ทดสอบ ยังไม่สรุปว่าเส้นทางอื่นเกิดเหมือนกันทั้งหมด

ขั้นตอนทำซ้ำ:

1. เปิดฟอร์มเพิ่มข้อมูลตารางทดสอบ และกรอกชื่องาน
2. ส่งคำขอบันทึกให้เซิร์ฟเวอร์ประมวลผลจนตอบ HTTP 200 แล้วจำลองให้การเชื่อมต่อขาดก่อนเบราว์เซอร์ได้รับคำตอบ
3. ตรวจฐานข้อมูล พบว่าบันทึกสำเร็จแล้วหนึ่งแถว
4. หน้าจอยังคงข้อมูลในฟอร์ม พร้อมคำเตือนว่าผลอาจบันทึกแล้วและให้ตรวจรายการล่าสุด ปุ่มบันทึกกลับมากดได้
5. กดบันทึกอีกครั้ง พบว่ามีอีกแถวเพิ่มขึ้นจากข้อมูลชุดเดิม

ผลจริง: เกิดแถวสมมติ ID 63 และ 64 จากการบันทึกที่ผู้ใช้เข้าใจว่าเป็นการลองใหม่ ระบบมีคำเตือนอยู่แล้ว จึงไม่ได้เป็นกรณีไม่มีคำเตือน แต่ยังไม่ได้รับประกันว่าคำขอซ้ำของการบันทึกครั้งเดียวจะไม่สร้างแถวใหม่

ผลที่เสนอให้รองรับ: การลองส่งซ้ำของความตั้งใจบันทึกครั้งเดิมควรคืนผลเดิม ไม่เพิ่มแถวซ้ำ ส่วนการเปิดฟอร์มใหม่เพื่อเพิ่มอีกรายการต้องยังทำได้ตามปกติ แม้เนื้อหาจะเหมือนกัน

หลักฐาน:

- `artifacts/exploratory-2026-11-18/evidence.json`: ผลตอบกลับแรก 200 และรหัสแถวที่เกิดขึ้นสองแถว
- `artifacts/exploratory-2026-11-18/lost-response-error.png`: หน้าจอเมื่อการตอบกลับสูญหาย
- `artifacts/exploratory-2026-11-18/duplicate-after-network-retry.png`: รายการซ้ำสองแถว
- `app/components/RuntimeTable.tsx:273`: ส่งคำขอบันทึกผ่านตัวส่งฟอร์ม
- `app/components/RuntimeTable.tsx:294`: เก็บข้อผิดพลาด และ `:295` ปลดสถานะกำลังบันทึก
- `lib/pending-images.ts:48`: ตัวส่งฟอร์ม JSON/รูปภาพ เส้นทางที่ตรวจยังไม่มีรหัสคำขอสำหรับคืนผลเดิม
- `app/api/data/[table]/route.ts:117`: เส้นทางสร้างแถวเรียกบันทึกด้วย ID ที่ยังไม่กำหนด
- `app/components/AuthProvider.tsx:37`: มีการแจ้งผลไม่แน่นอนเมื่อการเชื่อมต่อขาด ซึ่งทำงานตามที่ออกแบบไว้

ผลกระทบ: ข้อมูลธุรกิจอาจซ้ำ ผู้ใช้อาจเข้าใจผิดว่าครั้งแรกไม่สำเร็จ หากแอปมี Automation ตอนสร้างแถว อาจมีผลข้างเคียงซ้ำด้วย ประเด็น Automation เป็นผลกระทบที่คาดได้จากการสร้างสองแถว แต่ยังไม่ได้ทดสอบการส่งอีเมลหรือ Push จริงในกรณีนี้

แนวทางแก้ที่เสนอ:

- เพิ่มรหัสคำขอเฉพาะการบันทึกหนึ่งครั้ง คงรหัสเดิมเมื่อลองส่งใหม่ และเปลี่ยนรหัสเมื่อเปิดฟอร์มใหม่จริง
- ผูกผลคำขอกับผู้ใช้ แอป พื้นที่พัฒนา ตาราง และลายนิ้วมือของข้อมูล ไม่ยอมให้คำขอเดิมถูกใช้กับข้อมูลคนละชุด
- บันทึกผลคำขอในธุรกรรมเดียวกับข้อมูลและการเตรียมงานเบื้องหลัง เพื่อป้องกันคำขอพร้อมกันและกรณีเซิร์ฟเวอร์เริ่มใหม่
- ใช้เส้นทางบันทึกเดิมและกฎธุรกิจเดิม ไม่สร้าง Action Engine ใหม่
- ไม่ใช้การห้ามชื่อซ้ำเป็นวิธีแก้ทั่วไป เพราะบางตารางมีข้อมูลเนื้อหาเหมือนกันอย่างถูกต้องได้

การทดสอบที่ต้องเพิ่มก่อนแก้: คำตอบสูญหายหลัง Commit การส่งพร้อมกัน คำขอเดิมแต่ข้อมูลเปลี่ยน ผู้ใช้ต่างกัน แอปต่างกัน ฟอร์ม Reopen รายการลูก รูปภาพ และจำนวนครั้งของงานเบื้องหลัง ต้องยืนยันว่าการส่งคำขอเดิมเพิ่มข้อมูลเพียงครั้งเดียว

### EXP-001 — View หลักของตารางใหม่ยังเริ่มเป็นรายการ

ประเภท: ความไม่สอดคล้องของค่าเริ่มต้นที่ยืนยันได้

ความสำคัญ: P3

ความมั่นใจ: สูง ทดสอบสร้างตารางใหม่สองครั้งแล้วได้ผลเดียวกัน

ผลจริง: ตารางใหม่สร้าง View หลักด้วย `kind=list` และแสดงการ์ดรายการ แม้แนวทางที่เคยขอไว้คือเริ่มต้นด้วยตาราง การเปลี่ยน View เป็นตารางด้วยตนเองยังทำงานได้

หลักฐาน:

- `lib/schema.ts:80`: กำหนด View หลักเป็น `list` ในฟังก์ชันสร้าง View อัตโนมัติ
- ผลจาก API ของตารางสมมติ `qa_tasks` และ `qa_default` มี View หลักแบบ `list`
- `artifacts/exploratory-2026-11-18/default-view-list.png`: ภาพหลังเปิดตารางที่เพิ่งสร้างโดยยังไม่ได้ปรับ View

แนวทางแก้: เปลี่ยนเฉพาะค่าเริ่มต้นของ View หลักที่สร้างใหม่เป็นตาราง ไม่เปลี่ยน View ของผู้ใช้ที่ตั้งค่าไว้แล้ว และไม่เปลี่ยน Inline หรือหน้ารายละเอียด/ฟอร์มตามไปด้วย ต้องยืนยันเงื่อนไขตารางภายนอกด้วยก่อนแก้

## ข้อจำกัดของผลตรวจ

- ไม่ใช่การรับรองว่าทุกฟีเจอร์ใน Repository ไม่มีบัค
- ยังไม่ได้ทดสอบ iPhone/Safari จริง การสลับแอประหว่างอัปโหลด เครื่องความจำน้อย หรือเครือข่ายมือถือจริง
- ไม่ได้ทำ Security Audit ครบทุก API หรือทดสอบโหลดผู้ใช้พร้อมกันจำนวนมาก
- ยังไม่ได้สำรวจ PDF แผนที่ ปฏิทิน การกู้คืนขนาดใหญ่ Push จริง และระบบภายนอกในรอบนี้
- ข้อมูลสมมติใช้สำหรับตรวจพฤติกรรมทั่วไป ยังไม่ครอบคลุมสูตรและการตั้งค่าทุกรูปแบบของแอปจริง
- ไม่มีการแก้ Source Code ในรอบสำรวจนี้ งานแก้ไขจากรอบก่อนยังคงอยู่ตามเดิม

## ลำดับที่แนะนำ

1. ป้องกันการสร้างข้อมูลซ้ำจากการลองบันทึกใหม่หลังผลตอบกลับไม่แน่นอน
2. ทำค่าเริ่มต้น View หลักของตารางใหม่ให้ตรงกับความต้องการ
3. ทดสอบซ้ำบน iPhone จริง โดยเน้นเน็ตสลับ Wi-Fi/มือถือ ย้ายแอป และการส่งรูปภาพ
