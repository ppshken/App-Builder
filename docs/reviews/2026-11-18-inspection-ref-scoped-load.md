# ลดเวลารอข้อมูลสูตรของ Inspection EDIT รอบสอง

## ปัญหาและขอบเขต

ผู้ใช้ทดสอบหลังปรับแคชรอบแรก พบเวลาประมาณ 4 วินาทีของคำขอข้อมูลสูตร จึงตรวจต่อโดยไม่เปลี่ยนฐานข้อมูลจริงหรือ Deploy

รอบแรกลดงานซ้ำ แต่ยังเตรียมประวัติการตรวจทั้งตารางให้การดึงคะแนนผ่าน Ref ทั้งที่หน้าจอแสดงรถเพียง 25 คัน รอบนี้ลดขอบเขตการโหลดเฉพาะคำขอแสดงข้อมูล `display=1`

## การแก้ไข

1. รวมคอลัมน์ปลายทางที่สูตร Ref ในหน้าจอเดียวกันต้องใช้ก่อนโหลด เพื่อให้คะแนนที่เป็นฐานของเกรดไม่ต้องคำนวณซ้ำแยกคำขอคอลัมน์
2. อ่านแถวรถที่ผู้ใช้มีสิทธิ์เห็นในหน้าปัจจุบัน คำนวณเฉพาะคอลัมน์ Ref และสูตรที่ Ref นั้นต้องใช้ แล้วโหลดปลายทางด้วยรหัสจริงที่อ้างอิง ไม่จำกัดจำนวนข้อมูลในฐานข้อมูลและไม่ตัดข้อมูลคะแนน
3. ระบุ `reference_scope` ในข้อมูลตอบกลับเพื่อบอกว่าไม่ใช่ข้อมูลทั้งตาราง ป้องกันสูตรรวมทั้งตารางใช้ข้อมูลบางส่วนโดยไม่รู้ตัว หากสูตรร้องขอข้อมูลทั้งตารางอย่างชัดเจน ให้กลับไปโหลดครบตามเดิม
4. การแสดงครั้งแรกที่ยังไม่ทราบรหัสแถวส่งข้อมูลประกอบที่ว่างพร้อมขอบเขต เมื่อได้แถวของหน้าแล้วจึงโหลด Ref ที่เกี่ยวข้อง และโหลดใหม่เมื่อเปลี่ยนหน้า
5. จำกัดการใช้งานนี้ด้วย `referenceOnly` ที่ API ตั้งให้เฉพาะการแสดงข้อมูล ฟอร์มแก้ไขและการทดสอบสูตรยังใช้พฤติกรรมเดิม เพราะผู้ใช้อาจเปลี่ยน Ref เป็นค่าที่ยังไม่ได้บันทึก ส่วน Action และการบันทึกข้อมูลไม่ใช้ขอบเขตใหม่นี้
6. ยังคงตรวจสิทธิ์อ่านและเงื่อนไขระดับแถวทั้งรถและปลายทาง ไม่ใช้ข้อมูลแถวที่ส่งมาจากผู้ใช้ตัดสินค่าจริง และไม่แบ่งแคชระหว่างคำขอ

ไฟล์หลักที่เกี่ยวข้อง:

- `lib/expression-context.ts`: รวมแผนคอลัมน์ หารหัส Ref จากแถวที่มีสิทธิ์อ่าน และโหลดเฉพาะรหัสปลายทาง
- `lib/expression.ts`: แยกการดึง Ref ตามรหัสออกจากการอ่านตารางทั้งชุด ตรวจขอบเขต Ref/Related
- `app/api/expression-data/route.ts`: เปิดขอบเขต Ref เฉพาะคำขอแสดงข้อมูล
- `app/components/RuntimeTable.tsx`: รู้จักข้อมูล Ref ที่มีขอบเขตและโหลดให้ตรงกับหน้าปัจจุบัน

## ผลวัดกับฐานข้อมูลบนเครื่องพัฒนา

เปิดฐานข้อมูลด้วย `readonly: true` และ `fileMustExist: true` ใช้บริบทเจ้าของจำลอง ไม่บันทึกแถวจริงหรือข้อมูลบัญชีจริงลงรายงาน วัดเครื่องเตรียมข้อมูลสูตร ไม่ใช่เวลา HTTP บน VPS หรือเวลารวมของหน้าจอ

| กรณี | ก่อนรอบสอง | หลังรอบสอง | ขนาดก่อน | ขนาดหลัง |
| --- | ---: | ---: | ---: | ---: |
| รถ 25 คันตามรหัสในคำขอที่ผู้ใช้แจ้ง | 4,550 มิลลิวินาที | 39 มิลลิวินาที | 3,037,606 ไบต์ | 4,434 ไบต์ |
| รถ 25 คันที่มีประวัติการตรวจ | 3,283 มิลลิวินาที | 646 มิลลิวินาที | 3,037,606 ไบต์ | 239,254 ไบต์ |

เปรียบเทียบด้วยการนำข้อมูลประกอบสูตรก่อนและหลังไปคำนวณค่ารถทั้ง 25 แถว รวมทุกคอลัมน์ แล้วจัดลำดับชื่อคีย์ก่อนเทียบแฮช ผลตรงกันทั้งสองกรณี ข้อมูลประกอบปลายทางตั้งใจลดลง จึงไม่ใช้แฮชของข้อมูลประกอบทั้งหมดเป็นเกณฑ์ว่าต้องเท่ากันเหมือนรอบแรก

หลักฐาน:

- `.test-data/inspection-narrow-comparison-final.log`
- `.test-data/inspection-narrow-history-final.log`

ตัวเลขเป็นการวัดครั้งเดียวในแต่ละกรณีบนเครื่องพัฒนา ภาระเครื่องและข้อมูลของหน้าที่แสดงมีผลต่อเวลา ไม่ใช่คำรับประกันว่าทุกหน้าจะใช้ 39 มิลลิวินาที

## การทดสอบ

- เพิ่มกรณี Ref แสดงเฉพาะรหัสที่ใช้จริง ทดสอบกับรุ่นก่อนแก้แล้วไม่ผ่าน เพราะโหลดทุกแถว หลักฐาน `.test-data/inspection-narrow-red.log`
- เพิ่มกรณีรวมคอลัมน์ Ref ที่ใช้สูตรร่วมกัน ทดสอบก่อนแก้พบโหลดตารางซ้ำสองครั้งแทนหนึ่งครั้ง หลักฐาน `.test-data/inspection-batch-red.log`
- ตรวจค่าที่ได้ การเปลี่ยนชุดรหัสหน้าใหม่ ค่าว่าง สูตรรวมทั้งตาราง และสิทธิ์ระดับแถว
- ตรวจว่าฟอร์มยังเปลี่ยน Ref เป็นรหัสอื่นที่ไม่ใช่ค่าเดิมในฐานข้อมูลได้และคำนวณคะแนนถูกต้อง
- ชุดทดสอบที่เกี่ยวข้องกับสูตร Ref/Related และตารางร่วม ผ่าน 63 ข้อ หลักฐาน `.test-data/inspection-narrow-targeted-final.log`
- ชุดทดสอบรวมรุ่นล่าสุด 659 ข้อ ผ่าน 652 ข้อ ข้าม 7 ข้อ ไม่มีข้อที่ล้มเหลว หลักฐาน `.test-data/inspection-narrow-unit-verified.log`
- เพิ่มการทดสอบ API และเบราว์เซอร์ใน `tests/ref-snapshot-browser.cjs` เรียกผ่าน `node scripts/integration.cjs refsnapshot` โดยบังคับใช้ฐานข้อมูลทดสอบแยก ตรวจการรอรหัสหน้าจอครั้งแรก การเปลี่ยนหน้า และทางถอยของสูตรทั้งตารางและฟอร์ม
- การทดสอบ API/เบราว์เซอร์ใหม่ผ่านบน Production Build พร้อมฐานข้อมูลทดสอบแยก รหัสจบงาน 0 หลักฐาน `.test-data/inspection-narrow-api-browser.log`
- การทดสอบ Related เดิมผ่านทั้งสูตร Action ฟอร์ม รายละเอียดมือถือ และสิทธิ์ระดับแถว รหัสจบงาน 0 หลักฐาน `.test-data/inspection-narrow-related-browser.log`
- Build รุ่นสุดท้ายผ่าน รหัสจบงาน 0 หลักฐาน `.test-data/inspection-narrow-build-verified.log` เครื่องมือหยุดแจ้งเตือนความปลอดภัยของ Next.js รุ่นเดิมหนึ่งรอบ จึงรันซ้ำเพื่อให้การตรวจ Build จบ ไม่ได้อัปเกรดแพ็กเกจในงานนี้

## ข้อจำกัด

- ถ้าสูตรต้องอ่านทั้งตารางจริง ระบบยังโหลดครบ การลดงานส่วนนั้นต้องวิเคราะห์สูตรและแผนคิวรีเพิ่มเติม
- เส้นทาง Ref ชั้นถัดไปที่ยังวางขอบเขตไม่ได้ยังโหลดแบบเดิม เพื่อรักษาผลลัพธ์
- ฟอร์มและการทำงานที่เกี่ยวกับค่าที่ยังไม่ได้บันทึกยังใช้เส้นทางเดิม
- ถ้าจำนวนรหัสปลายทางเกินเพดานสำหรับแผนโหลดแบบจำกัด ระบบกลับไปใช้การโหลดเดิม ไม่มีการตัดรหัสทิ้ง
- งานนี้ไม่เปลี่ยนแพ็กเกจ Next.js และไม่ Deploy
