## บัคใหม่ — EXP-20261119-001

### ฟอร์มสูญเสียค่าที่ยังไม่บันทึกเมื่อเพิ่มตารางอื่น

สถานะ: ยืนยันด้วย Runtime · ระดับ P1 · ความมั่นใจสูง

ทำซ้ำได้สามครั้งด้วยบัญชี Owner บนมือถือจำลอง ยังไม่ได้ยืนยันกับบัญชีทั่วไปหรือทุกเหตุการณ์เปลี่ยนสิทธิ์

ขั้นตอน:

1. สร้างตารางรถและตารางรายการตรวจที่มี Ref, Enum และช่องข้อความ
2. เปิดรายการตรวจใน Runtime แล้วเปิดฟอร์มเพิ่ม
3. พิมพ์ข้อความลงใน Note โดยยังไม่กดบันทึก
4. จากอีกฝั่งเรียกเพิ่มตารางใหม่ในแอปเดียวกัน ซึ่งไม่มี Ref หรือสูตรเกี่ยวกับตารางที่เปิดอยู่
5. หลังระบบรับข้อมูลตั้งค่าล่าสุด ช่อง Note กลับเป็นค่าว่าง

ผลที่คาด: ข้อมูลที่กรอกอยู่ควรคงเดิมเมื่อสิทธิ์ของตารางปัจจุบันไม่เปลี่ยน หรือมีการแจ้งเตือนก่อนทำลาย Draft

ผลจริง:

- ค่าก่อนสร้างตาราง: ข้อความ Draft ที่กรอกไว้
- ค่าหลังสร้างตาราง: ค่าว่าง
- DOM ของช่องกรอกถูกสร้างใหม่ (`sameInputNode: false`)
- ไม่แสดงคำเตือนข้อมูลยังไม่บันทึก (`discardDialogs: 0`)
- ขอบเขตสิทธิ์รวมเปลี่ยน แต่สิทธิ์ Dataset ของตารางที่กำลังกรอกยังเหมือนเดิม
- จำนวนรายการที่บันทึกแล้วไม่เปลี่ยน บัคนี้สูญเสียข้อมูลที่ยังไม่บันทึก ไม่ได้ลบแถวในฐานข้อมูล

หลักฐาน:

- `evidence.json`: `unsaved form while unrelated table is created`, `repeat unsaved form reset by unrelated table`, `access epoch resets unrelated form`
- ภาพก่อนเกิดปัญหา: `draft-before-schema-change.png`
- ภาพหลังเกิดปัญหา: `draft-after-schema-change.png`

สาเหตุจากหลักฐาน Runtime และเส้นทางโค้ด:

- `app/components/AuthProvider.tsx:32` โหลดสิทธิ์ใหม่เมื่อได้รับเหตุการณ์ข้อมูลตั้งค่าหรือ Realtime
- `app/run/page.tsx:32` เปรียบเทียบสิทธิ์รวมทั้งแอป เมื่อสิ่งใดเปลี่ยนจะเพิ่ม Permission Epoch
- `app/run/page.tsx:122` ใส่ Epoch นี้ใน Route Key และ Cache Scope
- `app/components/RuntimeTransition.tsx:17` ล้างหน้าที่เก็บไว้เมื่อ Cache Scope เปลี่ยน และบรรทัด 30 ล้างหน้าที่กำลังแสดง
- ผลที่วัดได้คือฟอร์มถูกสร้างใหม่โดยไม่มี Draft เดิม แม้สิทธิ์ของตารางปัจจุบันไม่เปลี่ยน

แนวทางแก้: แยกการเพิ่มตารางหรือสิทธิ์ที่ไม่เกี่ยวข้องออกจากการเพิกถอนสิทธิ์ของหน้าปัจจุบัน เก็บ Draft เมื่อสิทธิ์และโครงสร้างที่ฟอร์มใช้ยังเข้ากันได้ ห้ามแก้ด้วยการปิดการตรวจสิทธิ์หรือรักษาหน้าเดิมทุกกรณี

Regression Tests ที่ควรเพิ่ม:

- กรอกฟอร์มค้าง แล้วเพิ่มตารางอื่น ต้องคงค่าและไม่มี POST บันทึกอัตโนมัติ
- เพิ่มสิทธิ์ตารางที่ไม่เกี่ยวข้อง ต้องไม่ล้าง Draft
- ถอนสิทธิ์อ่านหรือแก้ไขตารางปัจจุบัน ต้องบล็อกการใช้งานตามเดิม
- เปลี่ยน App หรือบัญชี ต้องไม่ดึง Draft ข้ามบริบท
- ฟอร์มที่มีรูปและรายการลูกที่ยังไม่บันทึกต้องตรวจการเก็บ Draft แยกเพิ่ม ยังไม่ได้ทดสอบกรณีนี้ในรอบตรวจ

## บัคเดิมที่ยังยืนยันได้

### CONV-001 — การแปลงไม่ตรวจสิทธิ์ระดับแถวของบทบาทรายแอป

สถานะ: ยืนยันซ้ำ · P1 · ความมั่นใจสูง

สร้าง Text ที่มีค่า `true` และ `false` แล้วกำหนดสิทธิ์อ่านของบทบาทรายแอปเป็น `[value] = 1` ก่อนแปลงบัญชีทดสอบอ่านได้ 0 แถว Preview และ Apply Text → Yes/No ผ่านโดยไม่มีคำเตือน หลังแปลงบัญชีเดิมอ่านได้ 1 แถว ทั้งที่ไม่ได้แก้กฎสิทธิ์

หลักฐาน: `evidence.json` ส่วน `app role row rule conversion`

สาเหตุ: `lib/column-conversion.ts:87` ตรวจการใช้งานคอลัมน์เฉพาะ `_role_row_rules` ไม่ตรวจ `_application_role_rows` และบรรทัด 30 ไม่รวมข้อมูลสิทธิ์รายแอปใน Fingerprint ของ Preview

แนวทางแก้: ตรวจ Dependency ของสิทธิ์รายแอปในบริบทเดียวกับสิทธิ์เดิม และทำให้ผลตรวจหมดอายุเมื่อกฎสิทธิ์ที่เกี่ยวข้องเปลี่ยน ยังไม่ได้ทดสอบการแข่งขันเปลี่ยนกฎระหว่าง Preview/Apply ในรอบนี้

### CONV-002 — แปลงเป็น User ที่ไม่มีอยู่จริงได้

สถานะ: ยืนยันซ้ำ · P2 · ความมั่นใจสูง

Text `999999` แปลงเป็น User ได้ Preview อนุญาตและ Apply เก็บเลขนั้นจริง แต่ POST ปกติด้วยเลขเดียวกันได้ HTTP 400 ว่าต้องเลือกผู้ใช้ที่เปิดใช้งานและมีสิทธิ์เข้าแอป

หลักฐาน: `evidence.json` ส่วน `conversion to nonexistent User`

สาเหตุ: `lib/column-conversion.ts:137` ตรวจแถวด้วยเส้นทางที่ยังไม่เรียก `assertUserFields` ขณะที่การบันทึกปกติเรียกจาก `lib/permissions.ts:46` โดยมีตัวตรวจสมาชิกใน `lib/user-fields.ts:11`

แนวทางแก้: ใช้ข้อกำหนด User เดียวกับฟอร์ม และตรวจซ้ำก่อน Apply เมื่อผู้ใช้ถูกปิดหรือถูกถอนสิทธิ์

### CONV-003 — เปลี่ยนปลายทาง Ref ไม่ตรวจจำนวนรายการลูกของแม่ใหม่

สถานะ: ยืนยันซ้ำ · P2 · ความมั่นใจสูง

แม่เดิมกำหนดจำนวนลูก 1 แม่ใหม่กำหนดจำนวนลูก 2 มีลูกหนึ่งแถวพร้อมเงื่อนไข `COUNT([_THIS]) = [expected]` เปลี่ยน Ref ไปแม่ใหม่โดยจับคู่ ID ได้ Preview และ Apply ผ่าน แต่บันทึกแม่ใหม่ตามปกติได้ HTTP 400 เพราะรายการลูกไม่ผ่าน Valid_If

หลักฐาน: `evidence.json` ส่วน `Ref conversion child cardinality`

สาเหตุ: `lib/column-conversion.ts:150` ตรวจโครงสร้างด้วย `assertPartSchema` แต่ไม่ประเมินจำนวนลูกในบริบทแม่ใหม่แบบ `lib/part-of-records.ts:27` และ `lib/part-validation.ts:5`

แนวทางแก้: ตรวจแถวแม่ที่ได้รับผลกระทบทั้งก่อนและหลังเปลี่ยนปลายทาง แล้วใช้ตัวตรวจรายการลูกเดียวกับการบันทึกปกติ

## ลำดับแนะนำ

1. แก้ Draft หายจากการรีเฟรชขอบเขตสิทธิ์ และการตรวจสิทธิ์รายแอประหว่างแปลงข้อมูลก่อน
2. แก้ User และเงื่อนไขรายการลูกในการแปลงข้อมูล
3. ปรับชุดทดสอบเดิมสองจุดเพื่อให้ตรวจ Regression ได้ตรงและลดผลล้มเหลวจากจังหวะเวลา

## ยังไม่ได้ทดสอบ

iPhone/Safari จริง, VPS จริง, ความเร็วเครือข่ายมือถือจริง, Load Test หลายร้อยผู้ใช้, ทุกคู่ชนิดข้อมูล, การเปลี่ยนโครงสร้างทุกรูปแบบ, การกู้คืนสำรองทุกขนาด และผลกระทบต่อทุกบัญชีเมื่อมีการเปลี่ยนสิทธิ์ ยังไม่ถือว่าผ่านจากรอบนี้
